## 1. 环境：白捡的两个便宜

### 1.1 镜像自带可用的 PyTorch

第一次我按常规思路 `apt install python3-pip` + 建 venv + `pip install torch`（3GB 下载）。纯属浪费——
镜像里本来就有：

```
/usr/local/miniconda3/envs/py312/bin/python   Python 3.12.11
  → torch 2.13.0+cu132, cuda_available=True, GPU=NVIDIA GeForce RTX 4090
```

改成 `venv --system-site-packages` 继承它的 torch，只装缺的 5 个库，几分钟搞定。

**冒烟测试**：4090 上 bf16 矩阵乘实测 **146.2 TFLOPS**（理论峰值 ~165），卡是健康的。

### 1.2 学术加速已默认开启

pod 里预置了集群内代理，直接写在环境变量里：

```
http_proxy=http://mihomo.kube-system.svc.cluster.local:7890
https_proxy=（同上）
no_proxy=.svc,.cluster.local,10.42.0.0/16,...,.compshare.cn,.ucloud.cn
```

实测对比（同一台 pod，同一时刻）：

| 源 | 速度 |
|---|---|
| `huggingface.co`（走预置代理） | 185 KB/s |
| `hf-mirror.com` | **926 KB/s** |

**结论：代理可用但不是最快的，数据下载仍以 hf-mirror 为主**；代理的价值在于镜像站没有的资源
（GitHub Release、gated 仓库等）。`no_proxy` 已排除 `.compshare.cn`/`.ucloud.cn`，内网流量不走代理。

## 3. 训练数据：反向构造法

外部数据集全是英文、且 Schema 千差万别，**只能教格式不能教领域**。主力必须自造。

### 3.1 v1 的致命缺陷（值得单独记住）

第一版是"先采样槽位 → 再渲染文本"，产出的数据里有这种：

| 输入文本 | 标签 | 问题 |
|---|---|---|
| `加个七点半的闹钟` | `title: "午睡"` | 句子里根本没提"午睡"，标签凭空给了具体标题 |
| `设置个闹钟，早起` | `2026-01-12 15:30` | 句子完全没提时间，标签捏造了日期时间 |
| `下星期四9:00要报名` | `time: "21:00"` | 12 小时制把 21 点写成 "9:00"，标签与文本矛盾 |
| `排到下星期四13点` | `time: "13:45"` | 24 小时制分支**丢了分钟数** |
| `今天七点半` | `time: "19:30"` | period=none 时不该用 12 小时制去指代 19 点 |

**根因**：采样和渲染是两条独立路径，渲染时可能"漏说"某个字段，而标签里还带着它。

### 3.2 v2 的不变量

> **先决定要说哪些字段，文本只由这些字段渲染，标签也只由这些字段构造。
> 任何没说出口的字段，一律不进标签。**

配套三条硬约束：
1. `period=am/pm` 可用「上午九点」「晚上9:30」「21点30分」等无歧义写法；
2. `period=none` **只能用 1..12 点且不带前缀**，标签 time 用同一小时；
3. 24 小时制写法**必须带分钟**，否则 "13点" 会丢掉 45 分。

另外 `build()` 会返回一份"必须出现在句中的短语清单"，生成时逐条断言，不满足就丢弃该样本。

### 3.3 产出

## 4. 训练：性能调优是主要工作量

### 4.1 第一版慢得离谱

```
batch=1, accum=16, 在 __getitem__ 里实时做 apply_chat_template + 两次分词
→ 0.30 优化步/秒, GPU 利用率 19%, 功耗 84W(4090 TGP 450W)
→ ETA 11 小时
```

GPU 明显在挨饿。

### 4.2 两处修复

1. **预分词到内存**：把 Jinja 模板渲染和分词移出热路径（一次 4.2 秒完成全部 4000 条）
2. **真正的 batch**：`batch=8 × accum=2`（等效 batch 仍为 16）

### 4.3 结果

| 配置 | 优化步/秒 | GPU 利用率 | 功耗 | 全量训练耗时 |
|---|---|---|---|---|
| 第一版（batch=1，实时分词） | 0.30 | 19% | 84 W | ~11 小时 |
| **优化后（预分词 + batch=8）** | **2.39** | **93%** | **295 W** | **5.23 分钟** |

**提速 7.8 倍**，再加上每步处理 8 条样本，实际端到端快约 **140 倍**。

### 4.4 最终训练指标

```
LoRA r=16 alpha=32 dropout=0.05, target=q/k/v/o/gate/up/down_proj
可训练参数 10,092,544 / 606,142,464 = 1.67%
等效 batch 16, lr 2e-4 cosine + 3% warmup, bf16, max_len 640

训练完成: 750 步, 用时 5.23 分钟 (2.39 step/s)
验证集 loss: 0.0014 (372 条)
```

**loss 曲线**：step 1 = 1.71 → step 25 = 0.62 → step 75 = 0.017 → step 175 = 0.006 → 收敛到 0.0003。

> ⚠️ loss 低到 0.0003 说明**近乎完美地记住了这个模板分布**，这本身不能说明泛化能力——
> 真正的判断要看测试集精确匹配和分布外真实用例（见 §5）。

### 4.5 与本机 CPU 的对比（回答"5 小时够不够"）

| 硬件 | 配置 | 微批耗时 | 4000×3 epoch 全量 |
|---|---|---|---|
| 本机 Ryzen AI 9 365 CPU | 0.6B, seq256, bf16, 20 线程 | 3.74 s/微批 | **约 12.5 小时** |
| **Pod RTX 4090** | 0.6B, batch8, 预分词, bf16 | 0.21 s/微批 | **5.23 分钟** |

**约 140 倍差距。** 之前"本机 5 小时训一版"的估算虽然可行，但那是把数据压到 2000 条、只跑 1.6 epoch 换来的；
在 4090 上同样的 5 小时可以跑 **五十多轮**完整的 4000×3 训练。

## 5. 评测结果

### 5.1 测试集（372 条留出集，取前 300 条）

| 指标 | 结果 |
|---|---|
| 逐字段全等（严格） | **293/300 = 97.7%** |
| 逐字段全等（日期补零归一后） | **294/300 = 98.0%** |

失败样例的典型形态是 `"2026-12-1"` vs `"2026-12-01"` —— **纯格式差异，不是语义错误**。
→ 执行层应该 **解析日期而不是字符串比较**，这类问题自然消失。

### 5.2 真实用例（分布外，手写人话）

| 输入 | 输出 | 判定 |
|---|---|---|
| 为我的周二上午九点添加一个计算机原理的课程 | `{"module":"class",...,"when":{...,"time":"09:00","period":"am"}}` | OK |
| 下周三下午三点有高数考试 | `{"module":"exam",...,"week_ref":"next","time":"15:00"}` | OK |
| 加个明早八点的闹钟 | `{"module":"alarm",...,"time":"08:00","period":"am"}` | OK |
| 今天天气怎么样 | `{"status":"reject","commands":[]}` | OK |
| 帮我加个课 | `{"status":"clarify",...}` | OK |
| 周五之前要交操作系统实验报告 | `{"module":"assignment",...}` | OK |
| 周四下午两点在教三201开班会 | 正确带 `location` | OK |
| 记一下，我的快递取件码是 8823 | `{"module":"memo","notes":"8823"}` | OK |
| 麻烦帮我看看今天几号 | 判成 `clarify` | XX（应为 reject） |
| 我今天不想加日程，就是想问问你吃饭了没 | 判成 `clarify` 且复读用户原话 | XX（应为 reject） |
| 帮我把周三的组会改到周四 | 当成 `add` | --（训练集没有 update，属已知缺口） |

**通过率 11/13 = 85%。**

### 5.3 ⚠️ 最重要的发现：system prompt 就是模型契约

我第一次评测时用了这么一句"看起来更干净"的 system prompt：

```
你是日程助手，把用户的中文请求转换为 JSON，只输出 JSON。
```

结果 **真实用例 0/12，全军覆没**。模型完全无视我们的 Schema，自己发明了：

```json
{"action":"add","title":"计算机原理","when":"TU","time":"09:00","notes":"none"}
{"date":"WE","time":"15:00","subject":"高数考试"}
{"提醒":"明天晚上7:30","动作":"给家里打电话"}
```

换成训练时用的完整 system prompt（带 Schema 字段说明和规则）后，立刻变成 **11/13 = 85%**。

**教训**：微调后的模型是和**那一段特定的 system prompt** 绑定在一起的。它不是"学会了这个任务"，
而是"学会了在这个 prompt 下补全"。生产环境里：
- system prompt 必须**逐字节固定**，当成模型权重的一部分来管理（进 git、带版本号）；
- 改 prompt = 改了模型，必须重跑评测。

### 5.4 残留问题

| 问题 | 例子 | 对策 |
|---|---|---|
| 分布外表达出现**越界枚举值** | "周五之前…" → `fuzzy: "prev"`（不在枚举里） | **开约束解码（json_schema/grammar）**，这类错误结构上不可能出现 |
| 字段放错层级 | "今晚提醒我买牛奶" → `date_kind: "evening"` | 加更多 fuzzy 样本；执行层校验拦截 |
| `update`/`delete` 未覆盖 | "改到周四" 被当成 add | 训练集只做了 `add`，是已知范围限制 |
| `reject` / `clarify` 边界模糊 | "今天几号" 判成 clarify | 补充元问题类负样本 |

**这正好印证了前面架构分析的结论：约束解码负责"格式绝对合法"，LoRA 负责"语义尽量正确"，两者缺一不可。**
