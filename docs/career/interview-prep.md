# 面试准备包 · 基于 LoRA 微调后 Qwen3 的 AI 日程助手

> 用法：第一、二部分念到能顺口说出来；第三、八部分理解机制；第四部分只在卡壳时翻；第五、六、七部分临场前扫一眼。

## 一、项目介绍（口述稿，2 分钟）

这个项目是一个**本地跑的 AI 日程助手**。用户说一句"下周二上午九点加一门计算机原理，在教三201"，
本机的模型就把它转成结构化的工具调用，直接写进日历。再往上一层，用户也可以把一段很乱的
待办直接贴进来，系统先抽成任务和约束，再交给求解器排出一周的计划。整个过程中数据都在本机，
不上云。

模型我用了两个尺寸。日常加日程这种交互，延迟要求高，用的是微调过的 0.6B 模型；排周计划
要一次处理一大段文字，质量比速度更重要，所以另外挂了一个 4B。两个模型按场景分工，
拿一个去扛所有事，两头都不讨好。

工程上有三个我自己比较满意的决定。一是**不让模型碰日期计算**——契约里只允许"下周三"
这种相对说法，具体是哪天由后面的确定性代码算，这样"模型算错日期"这一类问题从源头就没了。
二是**排期不交给模型**，交给 CP-SAT 求解器，它算得快（二三十毫秒），排不出来的时候还能
告诉你到底是哪两条约束在打架。三是**整个项目只维护一份 JSON Schema**，约束解码的文法、
训练用的标签、执行前的校验、给客户端看的工具签名，全部从这一份派生，再用 CI 卡住，
防止各处悄悄改歪。

实测下来，在一台没有独立显卡的机器上，端到端中位数 641 毫秒，结构合规率 4372/4372。

## 二、模拟 Q&A

### 2.1 基础部分

**Q：这个项目解决什么问题？**
A：让模型说的话能真的被程序用起来。很多 demo 到"模型输出了一段 JSON"就结束了，但工程上
要求的是**这段 JSON 必须能被解析、而且语义是对的**。我的做法是把两件事拆开：理解语言
交给模型，算时间、排顺序交给确定性代码。模型只做它擅长的部分。

**Q：为什么不在云端跑？**
A：三个考虑。日程是很私人的数据，我不想让它出本机；每天几十次的调用量，用云端 API 成本
不划算；断网的时候也应该能用。代价是小模型能力弱一些，所以后面有相当一部分工作是在
用工程手段把这个差距补回来。

**Q：为什么用 0.6B 和 4B 两个模型？**
A：按延迟分。交互场景用户等不了，0.6B 在这台机器的核显上有 111 tok/s，够用；规划场景
一次要读进去一整段素材，我宁可等几秒换更高的抽取质量，所以用 4B（22 tok/s）。
拿一个模型通吃，要么慢得没法交互，要么准得不够用。

**Q：为什么选 LoRA 微调，而不是直接换更大的模型？**
A：这个我测过。1.7B 和 4B 的基座模型，在我这套新契约上零样本准确率只有 14% 和 19%——
**换大模型解决不了"它根本不会用这套契约"的问题**。LoRA 只训一对低秩旁路，显存和成本
都低一两个数量级，更重要的是能让模型学到训练数据里的**联合关系**，比如一段话里三件事
各自的时长、哪件事对应哪个截止日期。这种对应关系，靠给几个 few-shot 例子是补不出来的。

**Q：约束解码是什么？**
A：简单说，就是给模型的输出加一层"文法护栏"。推理的时候只能从符合语法的 token 里挑，
所以它写不出结构非法的东西。不过要清楚，这只保证格式对，**保证不了语义对**。

**Q：CP-SAT 在这里干什么？**
A：做带约束的排期。给它一批任务（各自的时长、截止、优先级）和一些"哪段时间不能排"的
限制，它返回一个满足所有硬约束、同时让软约束代价最小的周计划。它是确定性求解器，
同样的输入每次结果都一样，而且排不出来的时候能解释原因。

### 2.2 技术深入部分

**Q：约束解码具体是怎么做的？**
A：模型是逐 token 生成的，每步要在整个词表上挑一个，默认情况下十几万个 token 谁都有
可能被选中——所以才会出现引号没闭合、枚举里写了"开会"这种词、JSON 前后还带一句话。
约束解码是在**采样这一步**动手：先用一个状态机算出"按现在写到的位置，下一 token 允许是
哪些"，然后把不在允许集合里的 **logit 直接置成 -∞**。经过 softmax，-∞ 对应的概率就是 0，
是数学上的不可能，而不是"概率低所以大概不会发生"。这个状态机本质上是个下推自动机，
一直在跟踪语法走到哪儿了。

**Q：它有什么代价？**
A：三处。一是**首 token 会变慢**，因为文法要预先编译；二是**表达被限制**，Schema 里没定义
的字段模型压根生成不出来——所以设计契约本身就是在设计产品；三是 **token 边界问题**，
tokenizer 切词的方式不一定和语法边界对齐，状态机得处理"半个 token"的情况。
另外还有一点要主动说：它管不了语义。"开会"到底算 `meeting` 还是 `class`，模型照样可能判错，
所以执行层留了 `clarify`（反问）和 `reject`（拒答）两个出口，不让它硬凑一个形式合法的答案。

**Q：4B 为什么一度反而更差？**
A：这个坑我印象很深。Qwen3 默认开着 thinking，4B 会把 token 预算全花在推理链上，实测
输出了 298 个 reasoning chunk，**正文一个字都没有**。我先试了 `--reasoning-budget 0`，
没用——它只是把文本挪到 `content` 字段，模型该想还是想，而且还给出了错的年份。
真正管用的是 `--reasoning off`，关掉之后输出逐字一致，延迟从 1900ms 降到 641ms。

**Q：单一事实源怎么防止契约漂移？**
A：四处用的东西来源是同一个但用法不同：约束解码拿它生成文法，训练集生成器按它决定标签
有哪些字段，执行层用 Pydantic 镜像做校验，MCP 服务端用 `Literal[*SCHEMA_ENUM]` 直接取枚举。
光靠约定"改的时候记得同步"是不可靠的，所以我在 CI 里加了两条断言：Pydantic 的字段集合
必须等于 Schema，MCP 工具的枚举也必须等于 Schema。对不上就红。
漂移最麻烦的地方在于它**不报错**——训练时学的是 `remind_before`，线上校验要的是
`remind_before_min`，模型输出看着完全正常，但校验全挂。

**Q：反向构造怎么保证标签是对的？**
A：顺序反过来：**先有标签，再把标签渲染成文本**。标签直接从结构化真值生成，所以构造上
就不可能错。但渲染这一步可能漏说——比如文本里没提时长，标签却写了 120 分钟，那模型学到
的就是瞎猜。所以我又写了个校验器，逐条检查"标签里每个字段都能在文本里找到依据"，
而且是**按分句**查的，因为全文查会被别的事项的措辞打掩护。更关键的是，我给这个校验器
本身写了自测：故意把五类字段改坏，断言它必须全部抓到，同时干净数据必须零误报。
第一版自测我自己就写错了——把 `priority` 改成 `high`，可样本本来就是 `high`，等于没改，
结果误以为是校验器漏报。**一个永远通过的校验器其实等于没有校验器。**

**Q：规则层和模型怎么分工？会不会把模型本来对的改错？**
A：我的判断标准很朴素：**规则能做、而且做得更准的，就别交给模型**。模型抽禁排时段
（`keep_free`）只有 30.6%，但"周三上午别排东西"这种句式用正则几乎不会错，接管之后
提到了 94.4%。改坏的风险确实存在，我踩过两次：一次是把约束里的"周三"当成了事项的
截止日期，改成先把约束抽出来、记下它的字符区间、抹掉之后再给事项匹配日期；另一次是
标题和文本对不上时退化成全文查找，抓到别的事项的时长，改成定位失败就不改、保留模型原值。

**Q：现在 39%，怎么往 80% 走？**
A：短期靠微调。数据集和训练套件都已经就绪了（4000 条反向构造、标签 100% 校验通过），
只差一块 GPU。长期看要解决的是**联合自洽**：基座是逐 token 贪心，它没有"这条样本整体
要自洽"的意识，所以单看每个字段都对，凑一条就散了。微调教的正是这个。

## 三、技术扫盲（两块硬骨头）

### 3.1 约束解码：为什么"格式不可能非法"

模型不是一次吐出整段 JSON，而是一个 token 一个 token 往外蹦。每步在整个词表（十几万
token）上按概率挑一个，追加到末尾，再算下一个。默认情况下**谁都有可能被选中**，于是
自由生成会出这些错：

| 出什么错 | 长什么样 |
|---|---|
| 结构断裂 | `{"module": "meetin` 后面直接结束，引号没闭合 |
| 枚举越界 | `"module": "开会"` —— 词表里确实有这个词，但契约只允许 `meeting` |
| 画蛇添足 | JSON 前后多一句"好的，我帮你安排：…" |

说到底，**格式约束只存在于训练分布里，生成机制里并没有**。模型只是"倾向于"写对，
它没有任何机制**保证**写对。而工具调用这种事，解析失败就等于功能失败，没有容忍空间。

约束解码把它变成数学保证。它不做事后修补，而是在采样那一步介入：

```
每一步：
  ① 状态机给出"当前位置允许哪些 token"
  ② 不在允许集合里的，logit 置为 -∞
  ③ 剩下的做 softmax，再采样
```

因为 `-∞` 的指数是 0，非法 token 的概率**不是"很低"，而是恰好为零**。这个状态机其实就是
个下推自动机，一路跟踪语法位置：读到 `{"module": "` 就只允许枚举里的值，读到 `duration_min":`
之后就只允许数字。

> 面试时这么说：约束解码是在**解码器的采样层**做词表剪枝，用文法状态机把非法 token 的
> logit 屏蔽掉，让输出在语法上不可能违规。是采样层，不是后处理，这个区别要讲清楚。

GBNF 是 llama.cpp 用的文法描述语言，写法接近正则加 BNF：

```gbnf
root   ::= "{" "\"module\":" module "," "\"title\":" string "}"
module ::= "\"class\"" | "\"exam\"" | "\"meeting\"" | "\"alarm\""
```

不过项目里我没手写这些东西——llama.cpp 支持**从 JSON Schema 直接编译**（请求里带
`response_format: json_schema`）。所以只需要维护一份 Schema，文法自动就有了。

代价有三处，面试常追问：**首 token 延迟**，因为文法要预编译；**表达受限**，Schema 没定义的
字段根本出不来，所以设计契约本身就是在做产品设计；**token 边界问题**，tokenizer 的切词
方式不一定和语法边界对齐，状态机得处理"半个 token"。

但要说清楚一点：**它管不了语义。** 能保证 `module` 落在枚举里，保证不了"开会"该归
`meeting` 还是 `class`。所以执行层还有两个出口，`clarify`（信息不够就反问）和
`reject`（越界就拒答）。约束解码解决的是"能不能解析"，这两个出口解决的是"该不该执行"。

### 3.2 单一事实源：防的是"静默不一致"

同一份结构，项目里有四个地方要用：

| 谁在用 | 用来做什么 | 怎么得到 |
|---|---|---|
| 约束解码 | 生成文法，约束模型输出 | 把 Schema 交给 llama.cpp 编译 |
| LoRA 训练 | 决定训练标签有哪些字段和枚举 | 生成器读 Schema 构造标签 |
| 执行校验 | Pydantic 校验入参 | **镜像类**，字段一一对应 |
| MCP 工具 | `inputSchema` 给客户端看 | `Literal[*SCHEMA_ENUM]` 直接取枚举 |

如果这四处各写各的，麻烦不是"某天突然坏掉"，而是**慢慢变得不一致，直到某次上线炸掉**：

> 训练时模型学的字段叫 `remind_before`，线上校验要的是 `remind_before_min`。
> 模型输出完全正确，但校验全挂。而且**不报语法错**，最难查的就是这种。

这就是契约漂移。解法是只有 `schema/schedule_command.v2.json` 是人写的，其余几处全部派生。
Pydantic 那处为什么还要单独写个镜像类，不直接读 Schema？因为运行时要的是类型化对象和
逐字段校验，Schema 本身只是一份 JSON 描述，镜像类没法自动生成。既然生成不了，就用 CI
把它钉死：Pydantic 字段集合必须等于 Schema，MCP 工具枚举也必须等于 Schema。

说白了，**能让机器验的，就别指望人记得住**。

### 3.3 MCP 到底管什么（最容易混）

| 概念 | 管什么 | 不管什么 |
|---|---|---|
| Function Calling | 模型能不能调用函数 | 不管工具怎么被发现 |
| 提示词工程 | 怎么把话说清楚让模型照做 | 完全不管格式保证 |
| **MCP** | **工具怎么被描述、被发现、被调用** | 不管中文怎么变成 JSON |

**MCP 是工具层的标准化，它不在"翻译层"上。** 它的价值在于，任何支持 MCP 的客户端都能
零适配接进来——客户端自己 `tools/list` 把签名拿过去就知道了，不用读文档，也不用写胶水代码。

我们这边更有意思的一点是：这个 `inputSchema` 不是手写的，它和解码文法、训练标签是同一个
源头派生出来的。所以"模型能生成的 JSON"和"客户端看到的工具签名"，永远是同一套东西。

## 四、答不上来时的应对话术

1. **完全没听过** → "这块我没有深入了解，不敢乱讲。我的理解是它在解决 X 类问题，但具体
   机制我拿不准。如果工作中要用到，我会先把官方文档和最小可跑的例子过一遍，再来确认。"
2. **记得结论忘了推导** → "结论我记得是 X，但要我现场推一遍有点勉强。当时是实验出来的，
   我可以把怎么测的讲一下——你更关心结论还是方法？"
3. **被追问到盲区** → "这点我确实没考虑到。我猜影响可能在 A 和 B 两方面，但需要验证。
   您是指哪个方向？我想顺着补一下。"（把追问变成学习机会）
4. **数据记不准** → "具体数字我不敢保证，量级是 600 多毫秒，准确值在仓库的 benchmark 里。
   我更确定的是**相对关系**：关掉 thinking 之后快了大概 3.6 倍，输出还是逐字一致的。"
5. **被指出方案有问题** → "您说得对，这确实是个漏洞。我当时在 X 和 Y 之间选了 X，考虑的是……。
   按您说的改，我担心会引入 Z，您觉得 Z 可以接受吗？"（承认取舍，别硬辩）
6. **通用兜底** → "整体我还不确定，但有一点可以肯定：______。其余的我想确认完再说。"

- 主线：**模型不算日期 / 排期交给 CP-SAT / 单一事实源防漂移 / 反向构造 + LoRA**

## 六、项目架构

### 6.1 部署形态：手机上不跑模型

| 层 | 组件 | 职责 |
|---|---|---|
| **客户端** | Android（Kotlin + Compose）、浏览器 | 只做输入和展示，不跑模型 |
| **服务层** | FastAPI `:8800` | Pydantic 契约校验、时间解析、日历 REST、单页 UI、MCP 服务端 |
| **推理层** | llama-server `:18080` | json_schema → GBNF 约束解码；Qwen3-0.6B + LoRA（Q4_K_M，378MB） |
| **存储** | SQLite `schedule.db` | 日程与备忘持久化 |

调用链：`客户端 ──HTTP + X-Sched-Token──▶ FastAPI ──OpenAI 兼容接口──▶ llama-server`
（规划时会另外挂一个 Qwen3-4B 在 `:18998`，和 0.6B 分工）

之所以这么分，是因为手机只负责输入和展示就够了，推理和存储都留在电脑上。好处很直接：
手机不用跑模型、换手机不用迁数据、模型升级只改一处。

### 6.2 一次请求的完整路径

1. 用户说"下下周二上午九点加一门计算机原理，在教三201"
2. FastAPI 把 **system prompt + 用户输入 + json_schema** 一起发给 llama-server
3. **约束解码**开始工作，枚举外的值在这一步就被禁掉了，模型只能吐合法结构
4. 模型返回 `{week_offset: 2, time: "09:00"}`——**只做语义归一化，不含绝对日期**
5. FastAPI 做 **Pydantic 契约校验 + 一致性守卫**（比如查年份合法性，防止模型编出 2023 年）
6. `executor.py` 的 `resolve_time()` 把 `week_offset=2` 推成 `2026-10-06`，写库，返回卡片

### 6.3 一份 Schema，五处使用

| # | 谁在用 | 由 Schema 派生出什么 |
|---|---|---|
| 1 | llama.cpp | 约束解码用的 GBNF 文法 |
| 2 | gen_dataset.py | LoRA 训练标签的字段与枚举 |
| 3 | schema_models.py | Pydantic 校验镜像（逐字段比对） |
| 4 | MCP `tools/list` | 工具的 `inputSchema` |
| 5 | acceptance_v2.py | 验收断言的期望值 |

五处最后都汇到同一条 **CI 断言：零漂移**。

> **这里有个措辞要注意**：简历上为了省字数写的是"**四处**消费"（解码 / 训练 / 校验 / MCP），
> 仓库里实际是**五处**——还有一处是验收断言的期望值也由 Schema 派生。被对照仓库追问的时候，
> 直接说"简历里写了核心的四处，实际还有第五处验收断言"就行，说清楚反而显得熟。

这么做值不值？如果训练标签和线上校验用的不是同一份契约，模型学的和你想要的东西会**悄悄错开**，
而且是静默错开——训练 loss 照样往下掉，等上线才发现。做成单一事实源之后，改契约就变成
一次原子操作：改 JSON、跑生成器、跑 CI，一起变。

## 七、关键名词备忘录

## 八、几个晦涩概念的落地解释

> 第七节是"这个词什么意思"，这一节补的是"它在我代码里到底长什么样、为什么非得这么处理"。
> 面试如果顺着名词往下挖，多半会挖到这里。

### 8.1 "下推自动机"不是课本名词，它就是一个逐字符走的状态

听起来唬人，做的事很朴素：维护一个"现在语法走到哪儿了"的指针。比如已经读到
`{"module": "`，下一个位置就只可能是几个枚举值之一；读到 `duration_min":`，就只允许数字。
叫"下推"是因为遇到数组和嵌套对象时，要记住"还有几层括号没闭合"，得有个栈。
项目里这个状态机不是我写的，是 llama.cpp 把 Schema 编成 GBNF 之后自己维护的。

### 8.2 "token 边界问题"具体会出什么事

模型想输出 `"meeting"`，但 tokenizer 可能把它切成 `"meet` + `ing"`。如果状态机只在
"完整 token"粒度上判断，读到 `"meet` 时就无法判断后面能不能接 `ing"`。办法是让它接受
**部分匹配**：只要这个 token 是某个合法序列的前缀就放行，等后续 token 补完再确认。
代价是状态转移变复杂，这也是"首 token 延迟"的来源之一。理解到这层，被问"约束解码
为什么不是免费的"，就能答得比"因为要编译文法"更实。

### 8.3 为什么必须"按分句"检查，而不是全文检查

这是写数据校验器时踩的坑，很具体：一条样本里可能有三件事，A 说"两小时"、B 说"一下午"。
如果拿标签里的"120 分钟"去**全文**找依据，"两小时"确实出现过，检查通过——可这个"两小时"
是 A 的，B 的标签可能根本没有依据。所以改成先按标点和换行把文本切成分句，只在该事项
自己所在那句中找。**校验的精度取决于你圈定的范围**，范围越粗，漏掉的越多。

### 8.4 "联合分布"和"逐 token 贪心"差在哪

基座模型每次只挑当下概率最高的 token，它没有"我要生一条整体自洽的样本"这个意识。
表现出来就是：单看每个字段都对，凑一条就散了——比如三件事里两件时长对了，第三件却填了
默认值；或者截止日期填了，但填给了错误的那件事。这不是"模型不会"，而是**它在局部最优，
没在做全局约束**。微调之所以有用，是因为 4000 条样本把"这几件事、这几个时长、这几个截止
是绑在一起的"这个联合分布喂给了它，让它在这个任务上不再是纯局部贪心。反过来，这也解释了
为什么 few-shot 加例子效果有限——几个例子改变不了分布。

### 8.5 "软化约束"是怎么定位冲突的

正常的硬约束是"必须满足"，一旦不可行，求解器只会告诉你 INFEASIBLE，不会说为什么。
我的做法是重解一次：把所有硬约束改成**带高罚金的软约束**，目标函数里违规越重罚得越多。
这次一定能解出来，然后看哪些约束的罚金不为零——那些就是冲突源。比如"周四前必须交报告"
和"周三周四整天不能排事"同时存在，重解之后前者会带罚金，就能直接告诉用户"你这两条要求
互斥"。这比单纯说"排不出来"有用得多，也是我在二阶段最想保住的能力。

### 8.6 为什么 Pydantic 镜像不能自动生成

理论上可以从 JSON Schema 自动生成 Pydantic 模型，但我没这么做，原因是这个镜像类除了字段
定义，还承载了一些 Schema 表达不了的东西：一致性守卫（比如年份不能早于当前、`date_kind`
和 `date_value` 必须匹配）、字段之间的互斥关系、以及给人看的中文错误信息。这些是业务逻辑，
不是数据结构。所以我选择手写镜像，然后用 CI 断言保证"字段集合永远等于 Schema"——
把可以自动化的部分（字段名、枚举）交给机器盯，把不能自动化的部分（校验逻辑）留在人手里。

### 8.7 n_ctx 从 2048 提到 8192，为什么延迟没变差

一开始我担心扩上下文会让每次请求变慢。实际测下来中位数从 641ms 变成 593ms，属于噪声范围。
原因是 KV cache 只在**实际用到的长度**上计算——短请求只占几十个 token，窗口开到 8192 只是
多分配了点内存（llama-server 内存 1.59GB），计算量并没有增加。真正会变慢的是长 prompt，
也就是二阶段做 few-shot 和多轮对话的时候。这个结论对选型有用：**扩窗口几乎免费，
但要知道它的收益只在长输入时才体现。**
