# 面试准备包 · 基于 LoRA 微调后 Qwen3 的 AI 日程助手

> 用法：第一、二部分熟读能诵；第三部分理解机制；第四部分只在卡壳时翻；第五、六、七部分临场前扫一眼；第八部分是答追问的弹药库。

## 一、项目介绍（口述稿，2 分钟）

本项目是一个**基于微调后 Qwen3 模型的 AI 日程助手**。用户输入一句日程变更指令，如"下周二上午九点加一门计算机原理课，在教三201"，本机模型会输出一段**符合约定 Schema 的结构化指令 JSON**，执行器将它解释成具体的增删改操作并写入日历。用户还可以贴入一段杂乱的待办，系统先抽取成任务与约束，再交给 CP-SAT 求解器排出一周的计划。

开发过程中我做了以下三个重要决定。一是**不让模型负责日期计算**——契约里只允许"下周三"这种相对说法，具体是哪天由后面的确定性代码算，这样"模型算错日期"这一类问题从源头就消失了。二是**排期交给 CP-SAT 约束规划求解器而非模型**，CP-SAT 计算速度快（二三十毫秒），发生约束冲突时还能快速定位原因，天然适合处理日程规划问题。三是**整个项目只维护一份 JSON Schema 作为"说明书"**：约束解码器用的文法、以及给客户端看的工具签名，由代码工具根据它自动生成；训练用的标签、执行前的 **Pydantic** 校验无法完全自动生成，于是先手写一份镜像，再由 CI 断言校验字段与枚举，以防止契约漂移。

实测数据如下：在没有独立显卡的本机上，端到端耗时中位数 **641 毫秒**；**4372 条**数据集样本全部通过 Schema 校验，并且能够驱动执行器。

***ps：***

*需要声明的是：**我们没有使用**原生 function calling。模型输出的是一段受 Schema 约束的 JSON 命令信封，由自己的执行器解释执行。这样做的好处是——模型可以换成本地部署的小模型，输出契约完全可控，也不依赖具体厂商的 tool-call 接口。*

*CI 断言指在持续集成流水线中自动执行的校验规则：检查代码、数据或模型行为是否符合约定，一旦不符合就标红并阻断合并。本项目里它守的是"训练、解码、校验、工具描述四处用的必须是同一份契约"这条底线。*

## 二、模拟 Q&A

### 2.1 基础部分

**Q：这个项目解决什么问题？**
A：让模型说的话能真的被程序用起来。很多 demo 到"模型输出了一段 JSON"就结束了，但工程上要求的是**这段 JSON 必须能被解析、而且语义是对的**。我的做法是把两件事拆开：理解语言交给模型，算时间、排顺序交给确定性代码。

**Q：模型输出的是工具调用吗？用的是 function calling 吗？**
A：不是。模型输出的是一段**受 JSON Schema 约束的命令信封**，长这样：
`{status: "ok", commands: [{module, action, title, when: {...}}]}`。
它由我们自己的执行器解释、解析日期、落库。我没有使用原生 function calling，原因有两个：一是采用本地部署微调后的 Qwen3 小模型，那套接口未必支持；二是自己维护契约，训练、解码、校验、工具描述才能共用同一个源头。**代价是工作量大，好处是完全可控。**

**Q：为什么不在云端跑？**
A：训练阶段我租用了云服务器，但推理和日常运行放在本机，主要是三个考虑。一是**隐私**，日程属于高敏感个人数据，我不希望它离开本机；二是**成本**，每天几十次的调用量，长期租云或调用云端 API 都不划算；三是**可用性**，断网时也应该能用。而且 0.6B 模型在核显上就能跑到 111 tok/s，没有必要为推理单独租机器。

**Q：为什么用 Qwen3 0.6B，不是更大的模型？**
A：经过分析，微调后的 Qwen3 0.6B 足以胜任需求，项目成功的关键在于设计出一套 AI 模型与代码工具之间合理的分工结构。0.6B 在本机核显上的运行速度为 111 tok/s，处理一条加日程请求平均仅需几百毫秒。

更大的模型理论上确实更准，但根据我的实测：1.7B 和 4B 的基座模型在新契约上的零样本准确率只有 14% 和 19%——**换大模型解决不了"它根本不会用这套契约"**，依然需要 LoRA 微调。所以选择 0.6B，再用 LoRA 补能力。

**Q：为什么选 LoRA 微调？**
A：LoRA 只训练一对低秩旁路，显存和成本都低一两个数量级，迭代快。更关键的是它能让模型学到训练数据里的**联合关系**，比如一段话里三件事各自的时长、哪件事对应哪个截止日期。这类对应关系仅仅靠几个 few-shot 例子无法让模型学会。

**Q：约束解码是什么？**
A：简单来说，就是给模型的输出加一层"文法护栏"。推理时解码器只能从符合语法的 token 里挑，所以它的输出结构必然合法。不过这只保证格式对，**保证不了语义对**。

**Q：CP-SAT 在这里干什么？**
A：做带约束的排期。输入是一批任务（各自的时长、截止、优先级）和若干限制（"哪段时间不能排哪些任务"），它返回一个满足所有硬约束、同时让软约束代价最小的周计划。它是确定性求解器，同样的输入每次结果都一样，排不出来时还能解释原因。

### 2.2 技术深入部分

**Q：约束解码具体是怎么做的？**
A：模型是逐 token 生成的，每步要在整个词表上挑一个。默认情况下十几万个 token 谁都有可能被选中，所以才会出现引号没闭合、枚举里写了"开会"这种词、JSON 前后还多一句话这类非法输出。

约束解码在**采样这一步**入手：先用一个状态机算出"按现在写到的位置，下一 token 允许是哪些"，然后把不在允许集合里的 **logit 直接置成 -∞**。经过 softmax，-∞ 对应的概率是 0，即数学上的不可能，而不是"低概率"。这个状态机本质上是一个下推自动机，一直在跟踪语法走到哪儿了。

***ps：***

*Logits 是模型最后一层神经网络直接输出的数值（而非概率），可以理解为模型对每个候选词的"偏好分数"。*

*Softmax 是一个把任意实数向量转成概率分布的函数：`p_i = e^{z_i} / Σ e^{z_j}`。它保证所有输出落在 (0,1) 之间、总和为 1，且保留原有的相对大小关系。约束解码正是利用 `e^{-∞} = 0` 这一点——被置为 -∞ 的候选，概率严格等于 0，而不是"很小"。*

**Q：它有什么代价？**
A：三处。一是**首 token 会变慢**，因为文法要预先编译；二是**表达被限制**，Schema 里没定义的字段模型压根生成不出来——所以设计契约本身就是在设计产品；三是 **token 边界问题**，tokenizer 切词的方式不一定和语法边界对齐，状态机得处理"半个 token"的情况。另外还有一点：它保证不了语义准确。"开会"到底算 `meeting` 还是 `class`，模型依然可能错判，所以执行层留了 `clarify`（反问）和 `reject`（拒答）两个出口，不让它硬凑一个形式合法的答案。

**Q：4B 为什么一度反而更差？**
A：这一点我印象很深。Qwen3 默认开着 thinking，4B 会把 token 预算全花在推理链上，实测输出了 298 个 reasoning chunk，**正文一个字都没有**。我先试了 `--reasoning-budget 0`，没用——它只是把文本挪到 `content` 字段，模型该想还是想，而且还会给出错的年份。真正管用的是 `--reasoning off`，关掉之后输出逐字一致，延迟从 1900ms 降到 641ms。

**Q：单一事实源怎么防止契约漂移？**
A：整个项目只维护一份 JSON Schema 作为单一事实源，它规定了有哪些字段、哪些必填、枚举能取哪些值。四个地方以它为准，但"为准"的方式分两种。

**一种是自动派生。** 约束解码把整份 Schema 交给 llama.cpp 编译成 GBNF 文法；MCP 服务端用 `Literal[*SCHEMA_ENUM]` 直接读取枚举作为参数类型。调整 Schema，这两处会自动变更，不用改代码。

**另一种是手写镜像 + 机器校验。** 执行前的 Pydantic 校验和训练标签的生成器无法完全自动生成——比如 Pydantic 需要承载类型化对象、逐字段校验和中文报错信息，JSON Schema 表达不了这些。这两处先手写，再依靠 CI 断言验证：Pydantic 可以反推出自己的 JSON Schema，拿它和磁盘上的原件逐字段对比；训练的产物则用 `jsonschema` 整体校验。

***ps：***

*Pydantic 通过**类型注解、字段约束和自定义验证器**，在运行时自动校验数据，防止非法输入进入业务逻辑层。*

*契约漂移指同一份数据结构在多处各自手写，开发过程中逐步变得不一致。典型例子：训练时生成器手写的是 `remind_before`，Pydantic 校验手写的是 `remind_before_min`——模型输出语法完全正确，但校验全挂了。它的可怕之处在于**不报语法错**，训练 loss 照样下降，日志里看不出任何异常，往往上线了才发现。根本原因是"手抄"这个行为本身，所以解法是单一事实源：能自动派生的一律自动派生，必须手写的用 CI 断言锁死字段集合与枚举都等于 Schema。这样契约变更就变成一次原子操作：改 JSON → 跑生成器 → 跑 CI → 一起变。*

**Q：反向构造怎么保证标签是对的？**
A：顺序反过来：**先有标签，再把标签渲染成文本**。标签直接从结构化真值生成，所以构造上就不可能错。但渲染这一步可能漏说——比如文本里没提时长，标签却写了 120 分钟，那模型学到的就是瞎猜。所以我又写了个校验器，逐条检查"标签里每个字段都能在文本里找到依据"，而且是**按分句**查的，因为全文查会被别的事项的措辞打掩护。更关键的是，我给这个校验器本身写了自测：故意把五类字段改坏，断言它必须全部抓到，同时干净数据必须零误报。第一版自测我自己就写错了——把 `priority` 改成 `high`，可样本本来就是 `high`，等于没改，结果误以为是校验器漏报。**一个永远通过的校验器其实等于没有校验器。**

**Q：规则层（代码工具）和模型怎么分工？会不会把模型本来对的改错？**
A：我的判断标准是：**规则能做、而且做得更准的工作，就不交给模型**。比如用模型抽取禁排时段的准确率（`keep_free`）只有 30.6%，但"周三上午不排日程"这类句式用正则接管之后，准确率提升到 94.4%。至于错改的风险，确实存在，项目发生过两次：一次是对于"周三上午别给我排日程，把实验报告写完，四小时"这种句式，把本应表示禁排的"周三"当成了"撰写实验报告"这件事的截止日期，我的解决方案是先把约束抽出来、记下它的字符区间、抹掉之后再给事项匹配日期；另一次是模型概括的事项标题和原文对不上时，规则层会退化成全文查找，从而误抓了其他事项的时长，解决方案是先做模糊匹配定位标题，如果定位依然失败则保留模型原值。

## 三、技术扫盲（两块硬骨头）

### 3.1 约束解码：为什么"格式不可能非法"

模型不是一次吐出整段 JSON，而是一个 token 一个 token 往外蹦。每步在整个词表（十几万 token）上按概率挑一个，追加到末尾，再算下一个。默认情况下**任何 token 都有可能被选中**，于是自由生成会出现这几类错误：

| 出什么错 | 长什么样 |
|---|---|
| 结构断裂 | `{"module": "meetin` 后面直接结束，引号没闭合 |
| 枚举越界 | `"module": "开会"` —— 词表里确实有这个词，但契约只允许 `meeting` |
| 画蛇添足 | JSON 前后多一句"好的，我帮你安排：…" |

说到底，**格式约束只存在于训练分布里，生成机制里并没有**。模型只是"倾向于"写对，它没有任何机制**保证**写对。而"模型输出要能直接驱动程序"这件事，解析失败就等于功能失败，没有容忍空间。

约束解码把它变成数学保证。它不做事后修补，而是在采样那一步介入：

```
每一步：
  ① 状态机给出"当前位置允许哪些 token"
  ② 不在允许集合里的，logit 置为 -∞
  ③ 剩下的做 softmax，再采样
```

因为 `e^{-∞} = 0`，非法 token 的概率**不是"很低"，而是恰好为零**。这个状态机本质上是一个下推自动机，一路跟踪语法位置：读到 `{"module": "` 就只允许枚举里的值，读到 `duration_min":` 之后就只允许数字。

> 面试口径：约束解码是在**解码器的采样层**做词表剪枝，用文法状态机把非法 token 的 logit 屏蔽掉，让输出在语法上不可能违规。要注意强调"采样层"而非"后处理"。

GBNF 是 llama.cpp 使用的文法描述语言，写法接近正则加 BNF：

```gbnf
root   ::= "{" "\"module\":" module "," "\"title\":" string "}"
module ::= "\"class\"" | "\"exam\"" | "\"meeting\"" | "\"alarm\""
```

不过项目里没有手写这些——llama.cpp 支持**从 JSON Schema 直接编译**（请求中携带 `response_format: json_schema`）。因此只需维护一份 Schema，文法自动就有了。

代价有三处，面试常追问：**首 token 延迟**，因为文法要预编译；**表达受限**，Schema 没定义的字段根本出不来，所以设计契约本身就是在做产品设计；**token 边界问题**，tokenizer 的切词方式不一定与语法边界对齐，状态机需要处理"半个 token"。

但要说清楚一点：**它管不了语义。** 能保证 `module` 落在枚举里，保证不了"开会"该归 `meeting` 还是 `class`。所以执行层还有两个出口：`clarify`（信息不够就反问）和 `reject`（越界就拒答）。约束解码解决的是"能不能解析"，这两个出口解决的是"该不该执行"。

### 3.2 单一事实源：防的是"静默不一致"

同一份结构，项目里有四个地方要用：

| 谁在用 | 用来做什么 | 怎么得到 |
|---|---|---|
| 约束解码 | 生成文法，约束模型输出 | 把 Schema 交给 llama.cpp 编译（自动） |
| LoRA 训练 | 决定训练标签有哪些字段和枚举 | 手写生成器 + `jsonschema` 校验产物 |
| 执行校验 | Pydantic 校验入参 | **镜像类** + CI 逐字段比对 |
| MCP 工具 | `inputSchema` 给客户端看 | `Literal[*SCHEMA_ENUM]` 直接取枚举（自动） |

如果这四处各写各的，麻烦不是"某天突然坏掉"，而是**慢慢变得不一致，直到某次上线炸掉**：

> 训练时模型学的字段叫 `remind_before`，线上校验要的是 `remind_before_min`。
> 模型输出完全正确，但校验全挂。而且**不报语法错**，最难查的就是这种。

这就是契约漂移。解法是只有 `schema/schedule_command.v2.json` 是人写的，其余几处全部以它为准。Pydantic 那处为什么还要单独写个镜像类、不直接读 Schema？因为运行时需要的是类型化对象和逐字段校验，Schema 本身只是一份 JSON 描述，镜像类没法自动生成。既然生成不了，就用 CI 把它钉死：Pydantic 字段集合必须等于 Schema，MCP 工具枚举也必须等于 Schema。

说到底，**能让机器校验的，就不该依赖人的记性**。

### 3.3 MCP 到底管什么（最容易混）

| 概念 | 管什么 | 不管什么 |
|---|---|---|
| Function Calling | 模型能不能调用函数 | 不管工具怎么被发现 |
| 提示词工程 | 怎么把话说清楚让模型照做 | 完全不管格式保证 |
| **MCP** | **工具怎么被描述、被发现、被调用** | 不管中文怎么变成 JSON |

**MCP 是工具层的标准化，它不在"翻译层"上。** 它的价值在于，任何支持 MCP 的客户端都能零适配接进来——客户端自己 `tools/list` 把签名取过去就清楚了，不用读文档，也不用写胶水代码。

我们这边更有意思的一点是：这个 `inputSchema` 不是手写的，它和解码文法、训练标签是同一个源头出来的。所以"模型能生成的 JSON"和"客户端看到的工具签名"，永远是同一套东西。

## 四、答不上来时的应对话术

1. **完全没听过** → "这块我没有深入了解，不敢乱讲。我的理解是它在解决 X 类问题，但具体机制我拿不准。如果工作中要用到，我会先把官方文档和最小可跑的例子过一遍，再来确认。"
2. **记得结论忘了推导** → "结论我记得是 X，但要我现场推一遍有点勉强。当时是实验出来的，我可以把怎么测的讲一下——您更关心结论还是方法？"
3. **被追问到盲区** → "这点我确实没考虑到。我猜影响可能在 A 和 B 两方面，但需要验证。您是指哪个方向？我想顺着补一下。"（把追问变成学习机会）
4. **数据记不准** → "具体数字我不敢保证，量级是 600 多毫秒，准确值在仓库的 benchmark 里。我更确定的是**相对关系**：关掉 thinking 之后快了大概 3.6 倍，输出还是逐字一致的。"
5. **被指出方案有问题** → "您说得对，这确实是个漏洞。我当时在 X 和 Y 之间选了 X，考虑的是……。按您说的改，我担心会引入 Z，您觉得 Z 可以接受吗？"（承认取舍，别硬辩）
6. **通用兜底** → "整体我还不确定，但有一点可以肯定：______。其余的我想确认完再说。"

## 五、面试前 5 分钟速览

- 三个诚实点：抽取准确率还不够、多轮对话没做、微调因为缺算力没跑
- 一个要主动澄清的点：**没用原生 function calling**，是 Schema 约束输出 + 自有执行器
- 收尾：**"这个项目我最想讲的其实不是功能，而是怎么把一个不确定的模型，安稳地放进一套确定性的工程里。"**

## 六、项目结构：模块与分工

整个项目可以按"三层分工 + 四条链路"来理解。三层分工是**核心设计**，四条链路是它跑起来的样子。

### 6.1 三层分工：谁负责什么

这是全项目最重要的一张表。模型、规则层、求解器各管一段，边界划得很清楚。

| 层 | 谁来干 | 负责什么 | **不负责什么** |
|---|---|---|---|
| **① 理解层** | Qwen3 模型（+ LoRA） | 判断该不该拒答、抽出有哪几件事、把中文表达归一化成结构化字段（"两小时"→120，"下下周二"→`week_offset=2`） | **不做任何计算**：不算绝对日期、不算结束时间、不排顺序 |
| **② 精确读取层** | `rules.py`（正则） | 文本里有明确字面依据时，逐字读出来覆盖模型——约束、日期说法、显式时长 | **不做语义判断**：不决定有几件事、不给事项分类、不估时长 |
| **③ 计算与求解层** | `executor.py` / `planner.py` | 相对时间→绝对日期；时长→结束时间；带约束排周计划 | **不猜语义**：输入什么就算什么，语义错了它不管 |

**为什么这样分**：因为这三件事的能力来源完全不同。理解靠模型，字面读取靠正则（确定性、100% 可复现），计算靠代码（可单测、可穷举）。**把能力来源不同的活儿混在一起，就没法分别验证。**

还有一条贯穿全项目的约束：**模型全程不碰绝对日期**。它最多输出 `week_offset=2`，由 `executor.resolve_time()` 推成 `2026-10-06`。这样做是因为模型算错日期是**静默失败**——错一周在界面上看不出来，用户不会报错，只会某天发现事没做。

### 6.2 各模块职责速查

| 模块 | 层 | 干什么 | 谁调用它 |
|---|---|---|---|
| `app.py` | 服务/编排 | Web 服务、拼 prompt 调模型、契约校验、日历 REST、单页 UI、MCP 挂载 | 客户端 |
| `schema_models.py` | ② 校验 | Pydantic 镜像，逐字段校验模型输出；与 Schema 的差由 CI 断言守 | `app.py` |
| `executor.py` | ③ 计算 | 相对时间→绝对时间；增删改查落 SQLite | `app.py` |
| `llama-server` | ① 推理 | 加载 Qwen3-0.6B + LoRA，跑约束解码 | `app.py` |
| `rules.py` | ② 读取 | 正则补抽 `keep_free` / 时长 / 日期说法 | `planning.py` |
| `planning.py` | ① 编排 | 二阶段抽取出 `planning_request`（文本→待办+约束） | `app.py` `/api/plan` |

### 6.3 四条链路

**训练链路（离线）**：`gen_dataset.py` 反向构造 4000 条 → `verify_dataset_e2e.py` 逐条验证 Schema 合规且能驱动执行器（4372 条零失败）→ `train_lora.py` 微调 → `convert_hf_to_gguf.py` → `llama-quantize` 量化成 Q4_K_M（378MB）。

**推理链路（在线，一次请求的 7 步）**：

| # | 环节 | 做什么 |
|---|---|---|
| 1 | 用户输入 | "下下周二上午九点加一门计算机原理，在教三201" |
| 2 | `app.py` `generate()` | 拼 system prompt + 用户文本 + `json_schema`，发给 llama-server |
| 3 | `llama-server` | 约束解码，输出 `{status, commands:[{module, action, title, when}]}` |
| 4 | `schema_models.py` | Pydantic 校验 + 一致性守卫（如年份合法性），不合格直接拒 |
| 5 | `executor.py` | `resolve_time()` 把 `week_offset=2` 推成 `2026-10-06` |
| 6 | `SQLite` | 落库 |
| 7 | `app.py` | 返回结果卡片，客户端刷新日历 |

**规划链路（二阶段）**：`rules.py` 正则先抽约束与字面字段 → `planning.py` 让模型抽出 `planning_request` 信封（这一环 0.6B 做不了，实验用的是 4B）→ `planner.py` 用 CP-SAT 排出周计划（21–32ms）→ 不可行时软化约束重解，定位到具体冲突。

**集成链路（对外）**：`mcp_server.py` 以标准 MCP 工具暴露能力；Web 单页与 Android 客户端都只发 HTTP 请求给本机 FastAPI。

### 6.4 部署形态与客户端

| 层 | 组件 | 职责 |
|---|---|---|
| **客户端** | Android（Kotlin + Compose）、浏览器 | 只做输入和展示，不跑模型 |
| **服务层** | FastAPI `:8800` | 契约校验、时间解析、日历 REST、单页 UI、MCP 服务端 |

> 每个词三列：一句话解释 + 在本项目里怎么用。面试时被丢一个名词，照第二列答，第三列补场景。

| 名词 | 一句话解释 | 在本项目里 |

## 八、实例与场景：把难点讲透

> 这一节是"被追问到细节"时的弹药。每条都是一个真实发生过的场景，能顺着讲出机制、踩的坑、怎么改的。

### 8.1 契约漂移：一次真实的字段改名

**场景**：开发到 v2 时，想把"下周"的表达从枚举改成数值偏移——因为 `week_ref` 只有 `this/next/none`，表达不了"下下下周"，也表达不了"上周"。

```json
// v1
"week_ref": { "enum": ["this", "next", "none"] }

// v2
"week_offset": { "type": "integer", "minimum": -2, "maximum": 4 }
```

同样是"下周"，v1 写 `{"week_ref": "next"}`，v2 写 `{"week_offset": 1}`。

**如果只改了一半会怎样**：Schema 改了（解码文法自动跟着变），但 Pydantic 镜像里还写着 `week_ref`。模型老老实实输出 `{"week_offset": 1}`，语法完全合法。然后 Pydantic 一看——如果配了 `extra="forbid"` 就直接抛错、接口 500；如果没配，`week_offset` 被丢掉，日期解析成空。

**后者更可怕**：它不报错，只是这条日程没有时间。

**怎么防住的**：改 Schema 之后，CI 里的 `check_drift()` 会立刻报"Schema 有但 Pydantic 缺 -> week_offset / Pydantic 有但 Schema 缺 -> week_ref"，提交直接红。同时 `executor.py` 还留了 v1 的兼容分支（测试用例里有一条 `v1 week_ref=next 兼容`），保证旧格式的存量数据不会突然失效。

### 8.2 模型算日期：为什么"上周二"会被算成本周二

这是我在做验收测试时发现的问题，很有代表性。

**测试**：今天假设是 2026-11-02（周一），输入"上周二下午三点开会"，期望 `2026-10-27`。

**结果**：得到 `2026-11-03` —— 差了一整周。

**根因**：`executor.resolve_time()` 里有一句"如果本周的这一天已经过了，就顺延到下周"。这个逻辑本身是对的（用户周一问"周五"当然指本周五，但如果今天是周六问"周五"，应该指下周五）。但条件写成了 `week_offset <= 0` —— 把**用户明确说的过去**（`week_offset = -1`，"上周二"）也一并顺延了。

**为什么这个 bug 特别难发现**：`2026-11-03` 是一个完全合法的时间，界面正常显示，没有任何报错。用户看到"开会 11月3日"，可能以为是自己记错了。**这就是"静默失败"——错得很自然。**

**修法**：条件改成只对 `week_offset == 0`（也就是用户没修饰、只说"周二"）做顺延。现在 `上周二` 正确得到 `2026-10-27`。

**这件事更值得注意的是**：当时的验收测试**把这个 bug 的产物当成了期望值**（因为测试是按当时的代码行为写的），所以一直是绿的。我后来把测试改成"按运行当天动态计算期望值"，才暴露出问题。

### 8.3 规则层的两次误伤（完整走查）

**背景**：规则层要做的事，是**按事项去原文里逐字抄字段**。因为一句话里可能有好几件事，各自的时长、日期散在原文不同位置：

```
原文：写周报，半小时；读两篇论文，每篇一小时
              ↑30                ↑60
```

模型输出的是一个列表，规则层要给它逐条补字段，就必须回答"`读论文` 这条的时长，从原文哪一句抄？"——而两边的连接点只有一个：**标题**。

**第一次误伤：约束污染了事项的日期**

```
输入：周三上午别给我排东西，把实验报告写完，四小时。
```

正确的解析是：一条约束（周三上午禁排）+ 一件事（实验报告 240 分钟，**无截止日期**）。

当时的做法是按标点切分句，然后在"包含'实验报告'的那一句"里找日期。但这句话本身就是一整句：

```
「周三上午别给我排东西，把实验报告写完，四小时」
```

这句话里有个"周三"，于是被当成了实验报告的截止日 → 实验报告被错误地加上了"截止周三"。

**修法**：调整处理顺序——先把约束抽出来、同时记下它在原文里的字符区间，**把那段抹成空格**，再去给事项匹配日期。

```
原文：  周三上午别给我排东西，把实验报告写完，四小时
抹掉后：                    ，把实验报告写完，四小时
                             ↑ "周三"已经不存在了
```

这时再找日期，找不到 → 实验报告正确地没有截止日。

**沉淀的经验**：**抽一类信息的动作，会污染另一类信息的抽取环境。**所以要按"谁的语义边界更清晰"排序处理——先把结构清楚的（约束）剥离出去，剩下的再交给模糊的（事项）。

**第二次误伤：全文兜底抄错了别人的时长**

**场景**：模型给的标题常常是概括过的。原文写"读两篇论文"，模型的标题写成"读论文"。按标题去原文精确匹配，找不到。

当时写的是：找不到就扩大到全文碰碰运气。

```python
hits = [c for c in clauses if title in c]
scope = hits[0] if hits else text      # ← 找不到 → 扩大到全文
```

于是"读论文"去全文里找时长：

```
全文：写周报，半小时；读两篇论文，每篇一小时
                    ↑ 全文第一个时长 = 30
```

**30 是周报的，却被当成了读论文的。**

**为什么这是根本性的错误，而不是"精度变差"**：规则层的全部合法性，来自"我在这句话里找到了字面依据"。它不是在猜，是在抄。扩大到全文之后，抄到的就是**别的事项的依据**——依据本身失效了。

而且它比"不改"更糟：模型在时长上本来就有 87% 是对的，改错等于把对的干掉了。

**修法两层**：先用模糊匹配尽量定位到对的那一句（用标题里最长的、能在某个分句里找到的片段，至少 2 个字——"读论文"里的"论文"能命中）；还是找不到就**跳过，保留模型原值**。

```python
scope = _scope_for(title, clauses)
if scope is None:
    continue          # 没有依据 → 跳过，不动模型的值
```

**一个必须说清楚的诚实点**：我原以为这个 bug 导致时长准确率从 87.0% 掉到 83.3%。但改完之后重测，**还是 83.3%**——那个下降其实是噪声（n=239 时标准误约 3.3 个百分点，3.7 个点的差异只有 1.1 个标准误）。**这个 bug 是"原理上错了"，但没有被数据证实造成可见损失。** 修它是因为它会产生一类"自信的错答",而不是因为它拉低了指标。

### 8.4 约束解码：枚举外的"开会"是怎么被禁掉的

**场景**：模型想输出 `{"module": "开会"}`。"开会"这个词在中文语境里完全正确，词表里也确实有这个 token。但契约只允许 `class/exam/meeting/assignment/alarm/reminder/memo` 七个值。

**没有约束解码时**：模型按概率挑，"开会"有一定概率被选中。即使训练过，也只是"倾向于"不选——**没有任何机制禁止它**。

**有约束解码时**：解码器维护一个文法状态机。读到 `{"module": "` 这几位之后，状态机进入"只能是这七个枚举值之一"的状态。下一步采样前，把词表里其余十几万个 token 的 logit 全部置成 -∞。经过 softmax，"开会"的概率是 `e^{-∞} / Σ = 0`。

**这一步的关键是它发生在 softmax 之前**——不是在生成完之后检查、发现不对再重试，而是在概率分布形成的那一刻，非法选项就不存在了。顺带一提，token 边界是这套机制的隐藏成本：tokenizer 可能把 `"meeting"` 切成 `"meet` + `ing"`，状态机必须接受"部分前缀匹配"才能放行，这也是首 token 延迟的来源之一。

### 8.5 单一事实源：哪些自动派生，哪些手写 + 断言

很多人以为"单一事实源"就是"全部自动生成"。实际项目里必须分两半，这个区分能体现工程判断力。

**能自动派生的两处**：约束解码文法——把整个 `SCHEMA` 对象塞进 `response_format.json_schema`，llama.cpp 自己编译成 GBNF，一行代码没有手写文法；MCP 工具签名——`MODULES = CMD["module"]["enum"]` 从 Schema 读出枚举，`Literal[*MODULES]` 变成 Python 类型，改 Schema 就自动跟着变。

**必须手写的两处，以及为什么**：Pydantic 校验镜像只能手写，因为 Schema 只能表达"有哪些字段、什么类型"，而运行时需要的是类型化对象、字段间互斥、年份合法性守卫、中文报错信息——**这些是业务逻辑，不是数据结构**。训练标签生成器同理，怎么把真值渲染成中文这件事本来就没法从 Schema 派生。

**这个区分的价值**：面试官问"Pydantic 是怎么从 Schema 自动生成的？"，答"自动生成"就露馅了；答"没法自动生成，用 CI 断言锁死"反而显得你清楚每层的边界。

### 8.6 软化约束：排不出来时怎么定位冲突

**场景**：用户说"周四前必须交报告"，同时又说了"周三周四整天别排事"。CP-SAT 遇到这类矛盾，只会返回一个 `INFEASIBLE`，**不会告诉你为什么**。但用户需要知道"是我哪两条要求互相矛盾"。

**做法**：把硬约束全部改成**带高罚金的软约束**重解一次。

```
原来的硬约束：  end ≤ deadline                （必须满足）
改成软约束：    end ≤ deadline + 罚金变量
               目标函数 += 10000 × 罚金变量
```

这样一定能解出来。然后看哪个罚金不为零——**那就是冲突源**。在这个例子里，"周四前交报告"这条带了罚金，于是可以直接告诉用户："你要求周四前交报告，但又要求周三四整天不排事，这两条互斥。"这比单纯说"排不出来"有用得多。

### 8.7 反向构造：为什么标签能保证正确

**正向做法**是人工看一段话、标出"这里有两件事，各自多长、什么截止"——成本高，而且人也会标错。**反向构造**反过来：先采样结构化的真值，再套模板渲染成中文，标签直接就是那份真值，**构造上不可能错**。

**但有一个漏洞**：渲染可能漏说。比如真值里某件事的时长是 120，模板渲染时忘了写上——模型看到的文本里没有时长，标签却说 120，那它学到的就是"瞎猜也能得分"。

**所以加了第二道**：一个独立校验器，逐条检查"标签里每个字段，都能在文本里找到依据"——时长必须出现在分句里或属该标题的公认默认值；截止说法必须逐字出现；优先级必须有对应措辞（"必须"→high，"有空"→low）；`keep_free` 的"周X + 时段"组合必须出现。

**为什么按分句而不是全文查**：一条样本里可能有三件事，A 说"两小时"、B 说"一下午"。拿 B 的标签"120 分钟"去**全文**找依据，"两小时"确实出现过——检查通过，但那是 A 的。**校验的精度取决于圈定的范围。**

**最后，校验器本身也要被验证**：故意注入五类错误标签，断言它必须全部抓到，同时干净数据零误报。第一版自测我自己就写错了——把 `priority` 改成 `high`，可样本本来就是 `high`，等于没改，于是误以为是校验器漏报。**一个永远通过的校验器，其实等于没有校验器。**
