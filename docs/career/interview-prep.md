# 面试准备包 · 基于 LoRA 微调后 Qwen3 的 AI 日程助手

> 用法：第一、二部分念到能顺口说出来；第三部分理解机制；第四部分只在卡壳时翻；
> 第五、六、七部分临场前扫一眼。

## 一、项目介绍（口述稿，2 分钟）

这个项目是一个**本地跑的 AI 日程助手**。用户说一句"下周二上午九点加一门计算机原理，
在教三201"，本机的模型会输出一段**符合约定 Schema 的结构化指令 JSON**，程序直接照着它
写进日历。再往上一层，用户也可以把一段很乱的待办贴进来，系统先抽成任务和约束，
再交给求解器排出一周的计划。整个过程数据都在本机，不上云。

这里有个容易被误解的地方，我先说清楚：**我们没有走原生 function calling**。模型输出的
是一段受 Schema 约束的 JSON 命令信封，由自己的执行器解释执行。这样做的好处是——模型
可以换成本地的小模型，输出契约完全可控，也不用依赖某家厂商的 tool-call 接口。
代价是这些活儿得自己实现。

模型我用了两个尺寸，但要说明白：**线上默认只跑一个是 0.6B**。日常加日程延迟要求高，
0.6B 在核显上有 111 tok/s，够用。4B 是我在二阶段做规划抽取实验时手动另挂的，还没进
默认配置——规划一次要读进去一大段素材，质量比速度重要，所以我用 4B 验证了效果，
但它目前属于实验链路，不是产品默认形态。

工程上有三个我自己比较满意的决定。一是**不让模型碰日期计算**——契约里只允许"下周三"
这种相对说法，具体哪天由后面的确定性代码算，这样"模型算错日期"这一类问题从源头就没了。
二是**排期不交给模型**，交给 CP-SAT 求解器，它算得快（二三十毫秒），排不出来的时候
还能告诉你到底是哪两条约束在打架。三是**整个项目只维护一份 JSON Schema**，约束解码的文法、
训练用的标签、执行前的校验、给客户端看的工具签名，全部从这一份派生，再用 CI 卡住，
防止各处悄悄改歪。

实测在一台没有独立显卡的机器上，端到端中位数 641 毫秒；4372 条数据集样本全部通过
Schema 校验并能驱动执行器，失败 0 条。

## 二、模拟 Q&A

### 2.1 基础部分

**Q：这个项目解决什么问题？**
A：让模型说的话能真的被程序用起来。很多 demo 到"模型输出了一段 JSON"就结束了，但工程上
要求的是**这段 JSON 必须能被解析、而且语义是对的**。我的做法是把两件事拆开：理解语言
交给模型，算时间、排顺序交给确定性代码。

**Q：模型输出的是工具调用吗？用的是 function calling 吗？**
A：不是。模型输出的是一段**受 JSON Schema 约束的命令信封**，长这样：
`{status: "ok", commands: [{module, action, title, when: {...}}]}`。
它由我们自己的执行器解释、解析日期、落库。原生 function calling 那套我们没用，
原因有两个：一是想换成本地小模型，那套接口不一定支持；二是自己维护契约，训练、解码、
校验、工具描述才能共用同一个源头。**代价是这些都得自己写，好处是完全可控。**

**Q：为什么不在云端跑？**
A：三个考虑。日程是很私人的数据，我不想让它出本机；每天几十次的调用量，用云端 API
成本不划算；断网的时候也应该能用。代价是小模型能力弱一些，所以后面相当一部分工作
是在用工程手段把这个差距补回来。

**Q：为什么用 0.6B，不是更大的模型？**
A：先看场景。日常加日程是高频短交互，用户在等，0.6B 在这台的机器核显上有 111 tok/s，
一条请求几百毫秒，够用。大模型确实更准，但我实测过：1.7B 和 4B 的基座在我这套新契约上
零样本准确率只有 14% 和 19%——**换大模型解决不了"它根本不会用这套契约"**，该微调还是得微调。
所以先按延迟选 0.6B，再用 LoRA 补能力。

**Q：为什么选 LoRA 微调？**
A：LoRA 只训一对低秩旁路，显存和成本都低一两个数量级，迭代快。更关键的是它能让模型
学到训练数据里的**联合关系**，比如一段话里三件事各自的时长、哪件事对应哪个截止日期。
这种对应关系靠给几个 few-shot 例子补不出来。

**Q：约束解码是什么？**
A：简单说，就是给模型的输出加一层"文法护栏"。推理的时候只能从符合语法的 token 里挑，
所以它写不出结构非法的东西。不过要清楚，这只保证格式对，**保证不了语义对**。

**Q：CP-SAT 在这里干什么？**
A：做带约束的排期。给它一批任务（各自时长、截止、优先级）和一些"哪段时间不能排"的限制，
它返回一个满足所有硬约束、同时让软约束代价最小的周计划。它是确定性求解器，同样的输入
每次结果都一样，而且排不出来的时候能解释原因。

### 2.2 技术深入部分

**Q：约束解码具体是怎么做的？**
A：模型是逐 token 生成的，每步要在整个词表上挑一个，默认情况下十几万个 token 谁都有
可能被选中——所以才会出现引号没闭合、枚举里写了"开会"这种词、JSON 前后还带一句话。
约束解码是在**采样这一步**动手：先用一个状态机算出"按现在写到的位置，下一 token 允许是
哪些"，然后把不在允许集合里的 **logit 直接置成 -∞**。经过 softmax，-∞ 对应的概率就是 0，
是数学上的不可能，而不是"概率低所以大概不会发生"。这个状态机本质上是个下推自动机，
一直在跟踪语法走到哪儿了。

**Q：它有什么代价？**
A：三处。一是**首 token 会变慢**，因为文法要预先编译；二是**表达被限制**，Schema 里没定义
的字段模型压根生成不出来——所以设计契约本身就是在设计产品；三是 **token 边界问题**，
tokenizer 切词的方式不一定和语法边界对齐，状态机得处理"半个 token"的情况。
另外还有一点要主动说：它管不了语义。"开会"到底算 `meeting` 还是 `class`，模型照样可能判错，
所以执行层留了 `clarify`（反问）和 `reject`（拒答）两个出口，不让它硬凑一个形式合法的答案。

**Q：4B 为什么一度反而更差？**
A：这个坑我印象很深。Qwen3 默认开着 thinking，4B 会把 token 预算全花在推理链上，实测
输出了 298 个 reasoning chunk，**正文一个字都没有**。我先试了 `--reasoning-budget 0`，
没用——它只是把文本挪到 `content` 字段，模型该想还是想，而且还给出了错的年份。
真正管用的是 `--reasoning off`，关掉之后输出逐字一致，延迟从 1900ms 降到 641ms。

**Q：单一事实源怎么防止契约漂移？**
A：几处用的东西来源是同一个但用法不同：约束解码拿它生成文法，训练集生成器按它决定标签
有哪些字段，执行层用 Pydantic 镜像做校验，MCP 服务端用 `Literal[*SCHEMA_ENUM]` 直接取枚举。
光靠约定"改的时候记得同步"是不可靠的，所以我在 CI 里加了两条断言：Pydantic 的字段集合
必须等于 Schema，MCP 工具的枚举也必须等于 Schema。对不上就红。
漂移最麻烦的地方在于它**不报错**——训练时学的是 `remind_before`，线上校验要的是
`remind_before_min`，模型输出看着完全正常，但校验全挂。

**Q：反向构造怎么保证标签是对的？**
A：顺序反过来：**先有标签，再把标签渲染成文本**。标签直接从结构化真值生成，所以构造上
就不可能错。但渲染这一步可能漏说——比如文本里没提时长，标签却写了 120 分钟，那模型学到
的就是瞎猜。所以我又写了个校验器，逐条检查"标签里每个字段都能在文本里找到依据"，
而且是**按分句**查的，因为全文查会被别的事项的措辞打掩护。更关键的是，我给这个校验器
本身写了自测：故意把五类字段改坏，断言它必须全部抓到，同时干净数据必须零误报。
第一版自测我自己就写错了——把 `priority` 改成 `high`，可样本本来就是 `high`，等于没改，
结果误以为是校验器漏报。**一个永远通过的校验器其实等于没有校验器。**

**Q：规则层和模型怎么分工？会不会把模型本来对的改错？**
A：我的判断标准很朴素：**规则能做、而且做得更准的，就别交给模型**。模型抽禁排时段
（`keep_free`）只有 30.6%，但"周三上午别排东西"这种句式用正则几乎不会错，接管之后
提到了 94.4%。改坏的风险确实存在，我踩过两次：一次是把约束里的"周三"当成了事项的
截止日期，改成先把约束抽出来、记下它的字符区间、抹掉之后再给事项匹配日期；另一次是
标题和文本对不上时退化成全文查找，抓到别的事项的时长，改成定位失败就不改、保留模型原值。

**Q：现在 39%，怎么往 80% 走？**
A：短期靠微调。数据集和训练套件都已经就绪了（4000 条反向构造、标签 100% 校验通过），
只差一块 GPU。长期看要解决的是**联合自洽**：基座是逐 token 贪心，它没有"这条样本整体
要自洽"的意识，所以单看每个字段都对，凑一条就散了。微调教的正是这个。

## 三、技术扫盲（两块硬骨头）

### 3.1 约束解码：为什么"格式不可能非法"

模型不是一次吐出整段 JSON，而是一个 token 一个 token 往外蹦。每步在整个词表（十几万
token）上按概率挑一个，追加到末尾，再算下一个。默认情况下**谁都有可能被选中**，于是
自由生成会出这些错：

| 出什么错 | 长什么样 |
|---|---|
| 结构断裂 | `{"module": "meetin` 后面直接结束，引号没闭合 |
| 枚举越界 | `"module": "开会"` —— 词表里确实有这个词，但契约只允许 `meeting` |
| 画蛇添足 | JSON 前后多一句"好的，我帮你安排：…" |

说到底，**格式约束只存在于训练分布里，生成机制里并没有**。模型只是"倾向于"写对，
它没有任何机制**保证**写对。而"模型输出要能直接驱动程序"这件事，解析失败就等于功能失败，
没有容忍空间。

约束解码把它变成数学保证。它不做事后修补，而是在采样那一步介入：

```
每一步：
  ① 状态机给出"当前位置允许哪些 token"
  ② 不在允许集合里的，logit 置为 -∞
  ③ 剩下的做 softmax，再采样
```

因为 `-∞` 的指数是 0，非法 token 的概率**不是"很低"，而是恰好为零**。这个状态机其实就是
个下推自动机，一路跟踪语法位置：读到 `{"module": "` 就只允许枚举里的值，读到 `duration_min":`
之后就只允许数字。

> 面试时这么说：约束解码是在**解码器的采样层**做词表剪枝，用文法状态机把非法 token 的
> logit 屏蔽掉，让输出在语法上不可能违规。是采样层，不是后处理，这个区别要讲清楚。

GBNF 是 llama.cpp 用的文法描述语言，写法接近正则加 BNF：

```gbnf
root   ::= "{" "\"module\":" module "," "\"title\":" string "}"
module ::= "\"class\"" | "\"exam\"" | "\"meeting\"" | "\"alarm\""
```

不过项目里我没手写这些东西——llama.cpp 支持**从 JSON Schema 直接编译**（请求里带
`response_format: json_schema`）。所以只需要维护一份 Schema，文法自动就有了。

代价有三处，面试常追问：**首 token 延迟**，因为文法要预编译；**表达受限**，Schema 没定义的
字段根本出不来，所以设计契约本身就是在做产品设计；**token 边界问题**，tokenizer 的切词
方式不一定和语法边界对齐，状态机得处理"半个 token"。

但要说清楚一点：**它管不了语义。** 能保证 `module` 落在枚举里，保证不了"开会"该归
`meeting` 还是 `class`。所以执行层还有两个出口，`clarify`（信息不够就反问）和
`reject`（越界就拒答）。约束解码解决的是"能不能解析"，这两个出口解决的是"该不该执行"。

### 3.2 单一事实源：防的是"静默不一致"

同一份结构，项目里有四个地方要用：

| 谁在用 | 用来做什么 | 怎么得到 |
|---|---|---|
| 约束解码 | 生成文法，约束模型输出 | 把 Schema 交给 llama.cpp 编译 |
| LoRA 训练 | 决定训练标签有哪些字段和枚举 | 生成器读 Schema 构造标签 |
| 执行校验 | Pydantic 校验入参 | **镜像类**，字段一一对应 |
| MCP 工具 | `inputSchema` 给客户端看 | `Literal[*SCHEMA_ENUM]` 直接取枚举 |

如果这四处各写各的，麻烦不是"某天突然坏掉"，而是**慢慢变得不一致，直到某次上线炸掉**：

> 训练时模型学的字段叫 `remind_before`，线上校验要的是 `remind_before_min`。
> 模型输出完全正确，但校验全挂。而且**不报语法错**，最难查的就是这种。

这就是契约漂移。解法是只有 `schema/schedule_command.v2.json` 是人写的，其余几处全部派生。
Pydantic 那处为什么还要单独写个镜像类，不直接读 Schema？因为运行时要的是类型化对象和
逐字段校验，Schema 本身只是一份 JSON 描述，镜像类没法自动生成。既然生成不了，就用 CI
把它钉死：Pydantic 字段集合必须等于 Schema，MCP 工具枚举也必须等于 Schema。

说白了，**能让机器验的，就别指望人记得住**。

### 3.3 MCP 到底管什么（最容易混）

| 概念 | 管什么 | 不管什么 |
|---|---|---|
| Function Calling | 模型能不能调用函数 | 不管工具怎么被发现 |
| 提示词工程 | 怎么把话说清楚让模型照做 | 完全不管格式保证 |
| **MCP** | **工具怎么被描述、被发现、被调用** | 不管中文怎么变成 JSON |

**MCP 是工具层的标准化，它不在"翻译层"上。** 它的价值在于，任何支持 MCP 的客户端都能
零适配接进来——客户端自己 `tools/list` 把签名拿过去就知道了，不用读文档，也不用写胶水代码。

我们这边更有意思的一点是：这个 `inputSchema` 不是手写的，它和解码文法、训练标签是同一个
源头派生出来的。所以"模型能生成的 JSON"和"客户端看到的工具签名"，永远是同一套东西。

## 四、答不上来时的应对话术

1. **完全没听过** → "这块我没有深入了解，不敢乱讲。我的理解是它在解决 X 类问题，但具体
   机制我拿不准。如果工作中要用到，我会先把官方文档和最小可跑的例子过一遍，再来确认。"
2. **记得结论忘了推导** → "结论我记得是 X，但要我现场推一遍有点勉强。当时是实验出来的，
   我可以把怎么测的讲一下——你更关心结论还是方法？"
3. **被追问到盲区** → "这点我确实没考虑到。我猜影响可能在 A 和 B 两方面，但需要验证。
   您是指哪个方向？我想顺着补一下。"（把追问变成学习机会）
4. **数据记不准** → "具体数字我不敢保证，量级是 600 多毫秒，准确值在仓库的 benchmark 里。
   我更确定的是**相对关系**：关掉 thinking 之后快了大概 3.6 倍，输出还是逐字一致的。"
5. **被指出方案有问题** → "您说得对，这确实是个漏洞。我当时在 X 和 Y 之间选了 X，考虑的是……。
   按您说的改，我担心会引入 Z，您觉得 Z 可以接受吗？"（承认取舍，别硬辩）
6. **通用兜底** → "整体我还不确定，但有一点可以肯定：______。其余的我想确认完再说。"

## 五、面试前 5 分钟速览

- 主线：**模型不算日期 / 排期交给 CP-SAT / 单一事实源防漂移 / 反向构造 + LoRA**
- 三个数字：**641ms**、**4372 条样本零失败**、**全对率 4%→39%**
- 三个诚实点：抽取准确率还不够、多轮对话没做、微调因为缺算力没跑
- 一个要主动澄清的点：**没用原生 function calling**，是 Schema 约束输出 + 自有执行器
- 收尾：**"这个项目我最想讲的其实不是功能，而是怎么把一个不确定的模型，安稳地放进一套确定性的工程里。"**

## 六、项目结构：从模型到客户端

整个项目可以按"四条链路"来理解：**训练（离线）→ 推理（在线）→ 规划（二阶段）→ 集成（对外）**。

### 6.1 训练链路（离线，产出一个 GGUF）

| # | 环节 | 做什么 |
|---|---|---|
| 1 | `gen_dataset.py` | 反向构造 4000 条样本：先定标签，再渲染成中文，标签由构造保证正确 |
| 2 | `verify_dataset_e2e.py` | 逐条校验：Schema 合规 + 能驱动执行器。4372 条全部通过，failed=0 |
| 3 | `train_lora.py` | LoRA 微调，只训低秩旁路；prompt 段的 loss 被 mask 掉 |
| 4 | `convert_hf_to_gguf.py` | 合并权重，导出 f16 GGUF |
| 5 | `llama-quantize` | 量化成 Q4_K_M（378MB）/ Q8_0，供核显推理 |

### 6.2 推理链路（在线，一次请求从进入到落库）

| # | 环节 | 做什么 |
|---|---|---|
| 1 | 用户输入 | "下下周二上午九点加一门计算机原理，在教三201" |
| 2 | `app.py` `generate()` | 拼 system prompt + 用户文本 + `json_schema`，发给 llama-server |
| 3 | `llama-server :18080` | 约束解码：非法 token 的 logit 置 -∞。输出 `{status, commands:[{module, action, title, when}]}` |
| 4 | `schema_models.py` | Pydantic 校验 + 一致性守卫（如年份合法性），不合格直接拒 |
| 5 | `executor.py` | `resolve_time()` 把 `week_offset=2` 推成 `2026-10-06`——**模型全程不碰绝对日期** |
| 6 | `SQLite` | 落库 |
| 7 | `app.py` | 返回结果卡片，客户端刷新日历 |

### 6.3 规划链路（二阶段，文本进、计划出）

| # | 环节 | 做什么 |
|---|---|---|
| 1 | `rules.py` | 正则先抽 `keep_free` / 时长 / 日期说法（模型只有 30.6%，规则接管后 94.4%） |
| 2 | `planning.py` | 模型抽取 `planning_request` 信封 —— 这一环 0.6B 做不了，需要 4B |
| 3 | `planner.py`（CP-SAT） | 区间变量 + NoOverlap + 软硬约束 → 周计划，21–32ms |
| 4 | 不可行时 | 软化约束重解，定位到具体是哪几条冲突 |
| 5 | 输出 | 计划 JSON 交给客户端渲染 |

### 6.4 集成与客户端

| 层 | 组件 | 职责 |
|---|---|---|
| **对外协议** | `mcp_server.py`（MCP 服务端） | 4 个工具：`add_schedule_item` / `list_schedule` / `plan_week` / `describe_contract`。工具签名由 Schema 派生，任意 MCP 客户端零适配接入 |
| **Web 客户端** | `app.py` 内嵌单页 | 月历视图、一句话添加、素材转计划面板；两套主题（纸感 / 夜航）由 CSS 变量驱动 |
| **Android 客户端** | Kotlin + Compose + Material 3 | 三个 Tab（添加 / 日历 / 设置）、主题令牌与 Web 共用同一份 `tokens.json` |
| **接入鉴权** | FastAPI 中间件 | `SCHED_TOKEN` 请求头校验，客户端在设置页填写 |

调用关系上，**手机和浏览器都只发 HTTP 请求给本机的 FastAPI，模型和数据库全在电脑端**。
好处很直接：手机不用跑模型、换手机不用迁数据、模型升级只改一处。

## 七、关键名词备忘录

> 每个词三列：一句话解释 + 在本项目里怎么用。面试时被丢一个名词，照第二列答，第三列补场景。

| 名词 | 一句话解释 | 在本项目里 |
|---|---|---|
| **静默（失败）** | 出了错但**不报错、不崩、看起来正常**，只是结果错了 | 模型把"上周二"算成"本周二"——界面照常显示，用户某天才发现事没做 |
| **漂移（契约漂移）** | 同一份结构在多处手写，慢慢变得不一致 | 训练学 `remind_before`、校验要 `remind_before_min`，模型输出全对却校验全挂 |
| **Schema** | 用 JSON 描述"数据长什么样"的结构定义 | `schedule_command.v2.json` 定义 module 枚举、时间槽位等全部字段 |
| **契约** | 各方共同遵守的数据格式约定 | 模型输出、执行层入参、MCP 工具签名都以此为准 |
| **单一事实源** | 只在一个地方定义，其他地方都由它派生 | 只有那份 JSON 是人写的，其余几处全部派生 |
| **派生** | 由上级定义自动生成，而不是手抄一遍 | 用 `Literal[*SCHEMA_ENUM]` 从 Schema 取枚举当 MCP 参数类型 |
| **约束解码** | 生成时把不符合文法的 token 概率压到 0 | 保证模型输出的 JSON 在结构上不可能非法 |
| **解码语法 / GBNF** | llama.cpp 的文法描述语言，规定 token 的合法序列 | Schema 自动编译成 GBNF，逐 token 约束采样 |
| **logit 屏蔽** | 把候选 token 的分数置为 -∞，softmax 后概率恰为 0 | 枚举外的词（比如"开会"）在解码阶段就被禁掉 |
| **llama.cpp** | 用 C/C++ 写的高效本地推理引擎 | 本机跑 0.6B，核显上 111 tok/s |
| **GGUF** | llama.cpp 的模型文件格式 | 分发用 GGUF，378MB |
| **量化（Q4_K_M）** | 把权重压到 4bit，体积约为 fp16 的 1/4 | 0.6B 压到 378MB，核显内存放得下 |
| **LoRA** | 冻结原模型，只训一对低秩旁路矩阵 | 0.6B 上用 4000 条数据微调，显存成本低一两个数量级 |
| **训练标签** | 监督学习里"标准答案"那部分 | 由 Schema 决定字段，由反向构造保证正确 |
| **反向构造** | 先定结构化真值，再渲染成中文，标签天然正确 | 4000 条样本零人工标注，标签 100% 校验通过 |
| **CP-SAT** | 约束规划求解器，擅长排期、装箱这类组合问题 | 把待办和禁排时段排成一周计划，21–32ms |
| **软化约束** | 把硬约束改成高罚金的软约束重解，看谁被违反 | 排不出来时用它定位"到底是哪几条约束在打架" |
| **规则层** | 用确定性正则接管结构化字段的抽取 | `keep_free` 从 30.6% 提到 94.4%，这部分不交给模型 |
| **Pydantic 校验** | Python 的类型化数据校验，运行时抛错 | 执行前校验模型输出，字段缺失或类型错直接拒 |
| **MCP** | 工具如何被描述、发现、调用的标准协议 | 日程能力以标准工具暴露，任意客户端零适配接入 |
| **MCP 工具签名** | `inputSchema`，告诉客户端这个工具要什么参数 | 由 Schema 派生，与解码文法、训练标签始终一致 |
| **CI 断言** | 每次提交自动跑的检查，不通过就红 | 断言 Pydantic 字段集合与 MCP 枚举都等于 Schema |
| **FastAPI** | Python 的异步 Web 框架，自带 OpenAPI | 提供 `/api/chat`、`/api/plan`、日历 REST 和单页 UI |
| **Compose** | Android 的声明式 UI 框架 | 客户端三屏（添加 / 日历 / 设置）和两套主题 |
| **局部重排（plan_diff）** | 只改动受影响的那几条安排，不整周重算 | 下阶段实现，比整周重排容错性更好、更稳定 |
| **多轮协商** | 保留对话上下文，用户不满意可以继续调 | 下阶段实现，当前是单轮 |
| **thinking 模式** | Qwen3 默认先生成推理链再出正文 | 必须 `--reasoning off` 关掉，否则 4B 正文零输出 |
| **全对率** | 一条样本所有字段都正确的比例 | 当前 39%（规则层加持后），微调目标 80%+ |
