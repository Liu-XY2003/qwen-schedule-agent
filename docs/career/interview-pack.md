# 面试准备包 · 本地优先的 AI 日程助手

> 用法：一、二部分反复念到能自然说出来；三部分快速过一遍；四部分只在卡壳时用。
> 原则：**不会就说不确定，但把边界说清楚**——这比硬编更有说服力。

---

## 一、项目介绍（口述稿，约 2 分钟）

这个项目是一个**本地优先的 AI 日程助手**：用户用自然语言说"下周二上午九点加一门计算机原理在教三201"，
系统把它转成结构化的工具调用并落库；二阶段再进一步，用户贴一段杂乱的待办，
系统抽成约束、再用求解器排出一整周的计划。

它有两个关键设计。第一，**模型只做语义归一化，不做计算**——契约里只允许"下周三""下个月3号"
这类相对表达，绝对时间由确定性代码解析，这样彻底消掉"模型算错日期"这一整类错误。
第二，**规划交给求解器**。让 LLM 直接产出可行计划在公开基准上准确率只有三成量级，
所以我把它拆成"模型抽取约束 + CP-SAT 求解"，求解只要 20 到 30 毫秒，而且排不出来的时候
能说清是哪几条约束在打架，这是 LLM 做不到的。

工程上最得意的一点是**一份 JSON Schema 驱动四个消费方**：约束解码的语法、LoRA 训练标签、
执行层校验、MCP 工具定义，全部同源。CI 里有断言，改 Schema 忘了同步会直接红。
实测端到端中位 641 毫秒——这台机器没有独显，只有核显。

## 二、模拟 Q&A

### 2.1 基础部分

**Q：这个项目到底解决什么问题？**
A：把"人话"变成"可靠的工具调用"。难点不在理解中文，而在**输出必须 100% 合法、语义必须正确**。
我的做法是把不确定的部分（语言理解）和确定的部分（日期解析、排期）切开。

**Q：为什么不用 GPT-4 / 云端 API？**
A：三个理由——**隐私**（日程是最私人的数据之一，不该出本机）、**成本**（每天的日程操作量下调用费不划算）、
**可用性**（断网也要能用）。代价是小模型能力弱，所以我要用工程手段补。

**Q：什么是约束解码？**
A：把 JSON Schema 编译成**文法（GBNF）**，推理时每个 token 只能在文法允许的集合里采样。
效果是输出**结构上不可能非法**——引号不闭合、枚举写错这类错误从"偶发"变成"0"。
但它只保证格式，**不保证语义对**，这是下一层校验要解决的。

**Q：为什么坚持"模型不算日期"？**
A：因为模型做算术是**不可测的错**——错一周在界面上完全看不出来，用户不会报错、只会某天发现事没做。
把日期计算移到确定性代码里，这类 bug 就消失了，而且能被单元测试覆盖。

**Q：MCP 是什么？你为什么用它？**
A：MCP 是**工具怎么被描述、发现、调用**的标准协议。它替代的是"工具层"，不是"把中文变成 JSON"
那一层——这两件事经常被混为一谈。用它是因为客户端能零适配接入，工具发现是协议内建的。

**Q：CP-SAT 在项目里干什么？**
A：解带约束的排期。输入是待办（含时长、截止、优先级）和限制（哪段时间不能排），
输出是一个满足所有硬约束、并让软约束代价最小的周计划。它是**确定性求解器**，
结果可复现、可解释——排不出来时能指出冲突在哪。

### 2.2 技术深入部分

**Q：约束解码有代价吗？它"保证格式不保证语义"具体是什么意思？**
A：有两个代价。一是**首 token 延迟**，语法要预编译，模型大、Schema 复杂时编译要几百毫秒。
二是**表达受限**，Schema 里没定义的东西模型就出不来，所以契约设计本身就是产品设计。
语义层面：约束解码能保证 `module` 一定在枚举里，但保证不了用户说的"开会"该归到 `meeting` 还是 `class`。
所以我在执行层留了 `clarify`（信息不足就反问）和 `reject`（越界就拒答）两个出口，
不让模型硬凑一个看起来合法的答案。

**Q：你提到 4B 反而表现更差，为什么？**
A：因为 Qwen3 默认开 thinking，4B 会把 token 预算全花在推理链上——实测 298 个 reasoning chunk、
**正文一个字都没输出**，端到端 13 秒。我一开始试 `--reasoning-budget 0`，**无效**：
它只是把文本挪到 `content` 字段，模型还在乱想，而且给出了错误年份 2023。
真正有效的是 `--reasoning off`，关掉之后输出**逐字一致**，1900ms 降到 641ms。

**Q："一份 Schema 四处消费"具体怎么防漂移？**
A：四处的消费方式不同但来源相同：约束解码读它生成 GBNF；训练集生成器读它决定标签字段；
执行层用 Pydantic 镜像做校验；MCP 服务端用 `Literal[*SCHEMA_ENUM]` 直接取枚举。
CI 里有两条断言：Pydantic 镜像与 Schema 的字段集合必须相等；MCP 工具枚举必须等于 Schema 枚举。
所以"训练时是一个字段、调用时是另一个字段"这种静默失效在提交前就会被拦住。

**Q：反向构造的数据怎么保证标签是对的？你怎么证明？**
A：流程是**先有标签、再渲染文本**——采样结构化的真值（三件事、各自多久、什么截止），
再套模板渲染成中文，标签直接从真值生成，所以**构造上就不可能错**。
但渲染可能漏说：如果文本没说时长、标签却写了 120 分钟，模型就学到瞎猜了。
所以我写了一个独立校验器，逐条断言"标签每个字段都能从文本推断"，而且是**按分句**检查——
全文检查会被别的事项的措辞打掩护。更关键的是我给校验器写了自测：故意把五类字段改坏，
断言它必须全部抓到，同时断言干净数据 0 误报。**一个永远通过的校验器等于没有校验器**，
这一点我在第一版就踩过——当时把 `priority` 改成 `high`，但样本本来就是 `high`，等于没改。

**Q：规则层和模型的边界怎么划？会不会把模型本来对的答案改坏？**
A：边界标准是"**规则做得到且做得更准的，就不给模型**"。实测模型抽 `keep_free`（哪段时间别排事）
只有 30.6%，但"周三上午别排东西"这种句式正则几乎不会错，接管后到 94.4%。
改坏的风险确实存在，我踩过两次：一次是把约束里的"周三"当成事项的截止日期，
解法是**先抽出约束并记下字符区间、抹掉之后再给事项找日期**；一次是标题与文本对不上时
退化到全文查找、抓到别的事项的时长，解法是**定位不到就不改**，保留模型原值。

**Q：现在整条全对 39%，怎么上到 80%？**
A：两条腿。短期靠微调——数据集和训练套件已就绪（4000 条反向构造、标签 100% 校验通过），只差 GPU。
长期靠**联合分布**：基座模型逐 token 贪心，没有"整条样本要自洽"的概念，所以单字段都对、凑一起对不齐；
微调教的正是这个。另外会做 `plan_diff` 局部重排——比整周重排容错性高，单次错误影响面更小。

## 三、技术知识点扫盲

### 3.1 基础

| 概念 | 一句话 |
|---|---|
| **LoRA** | 冻结原模型，只训一对低秩矩阵（`r` 是秩，通常 16），显存和成本降一两个数量级 |
| **GGUF / 量化** | llama.cpp 的模型格式；Q4_K_M 是 4bit 混合量化，体积约为 fp16 的 1/4 |
| **约束解码** | 按文法限制每个 token 的候选集，使输出结构天然合法 |
| **GBNF** | llama.cpp 用的文法描述语言，可从 JSON Schema 自动转换 |
| **CP-SAT** | 约束规划 + SAT 求解器，擅长排期/装箱这类组合问题 |
| **NoOverlap** | CP-SAT 的约束：一组区间互不重叠 |
| **MCP** | 工具/上下文暴露的标准协议，管"描述、发现、调用"，不管"中文怎么变成 JSON" |
| **KV cache / n_ctx** | 上下文窗口；缓存随长度线性涨，`n_ctx` 2048→8192 增加内存但几乎不影响短请求延迟 |

### 3.2 技术深入

| 概念 | 要点 |
|---|---|
| **thinking mode** | Qwen3 默认先生成推理链再出正文；`--reasoning-budget 0` **不能**关闭它，必须 `--reasoning off` |
| **首 token 延迟 vs 总时长** | 约束解码拉高首字延迟（语法编译），但总时长可能更短（少走弯路）；评测要分开看 |
| **bf16 vs fp16** | 原生 bf16 需要 sm_80+；Turing（2080Ti）只有 fp16。`torch.cuda.is_bf16_supported()` 在 sm_75 上会**误报 True**（把模拟支持算进去了） |
| **逐 token 贪心 vs 联合自洽** | 单字段准确率相乘会急剧衰减；这就是"每个字段都对、整条却不对"的根因 |
| **Wilson 置信区间** | 小样本下比正态近似可靠。21 条样本的 95% CI 有 ±11 个百分点，**不足以支撑任何结论** |
| **软化硬约束求冲突** | 求解器不可行时，把硬约束改成高罚金的软约束重解，罚金非零的就是冲突源 |
| **反向构造** | 从标签生成文本，而非从文本标标签；标签正确性由构造保证，但必须校验"文本是否说了" |
| **契约漂移** | 多处手写同一结构导致逐渐不一致；解法是单一事实源 + CI 断言 |

## 四、答不上来时的应对话术

> 目标不是糊弄过去，而是**展示你知道边界在哪、以及你会怎么查**。

1. **完全没听过这个概念**
   > "这块我没有深入了解过，不敢乱说。我的理解是它应该在解决 X 类问题，但具体机制我不确定。
   > 如果工作里要用到，我会先看官方文档和最小可运行例子，再回来确认。"

2. **记得结论忘了推导**
   > "结论我记得是 X，但为什么是这样我得再推一遍。当时是实验得出的，我可以把测法讲一下——
   > 你要的是结论还是方法？"

3. **面试官追问到你的盲区**
   > "这个点我确实没考虑到。您这么一说，我猜影响可能在 A 和 B 两方面，但需要验证。
   > 您能说说是哪个方向的问题吗？我想顺着学一下。"（**把追问变成学习机会**）

4. **数据记不准**
   > "具体数字我不保证，量级是 641 毫秒这个档位，准确值在仓库的 benchmark 文档里。
   > 我更确定的是**相对关系**：关掉 thinking 之后快了约 3.6 倍，输出逐字一致。"

5. **被指出方案有问题**
   > "您说得对，这确实是个漏洞。我当时的选择是在 X 和 Y 之间取了 X，原因是……。
   > 如果按您说的改，我担心会引入 Z。您觉得 Z 是不是可以接受？"（**承认真实取舍，不硬辩**）

6. **需要现场思考的开放题**
   > "给我 30 秒理一下思路。" → 然后**先说框架再说细节**：
   > "我打算分三步：先确认输入边界，再选方案，最后想怎么验证。第一步……"

7. **通用兜底**
   > "总体我还不确定，但有一点我可以肯定：______。其余的我想确认完再说，避免给您错的判断。"
