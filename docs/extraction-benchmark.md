# 抽取能力实测：二阶段的关键未知数

> 2026-11 实测。这是二阶段投入大量开发前必须先量出来的数字。
> 复现：`local/bench_extraction.ps1`

## 结论先说

| 模型 | 零样本 | few-shot | 提升 |
|---|---|---|---|
| Qwen3-1.7B | **14%**（3/21） | **33%**（7/21） | 2.4× |
| Qwen3-4B | **19%**（4/21） | **52%**（11/21） | 2.7× |

**两条明确结论：**

1. **不能直接换个大模型就用。** 基座模型面对全新的复杂契约，零样本几乎不会用
   （1.7B 有 17/21 直接输出 `reject`，把正常待办当成"与日程无关"）。
2. **few-shot 是廉价且必要的补丁，但 52% 仍不可用。** 想上 85%+，
   必须像一阶段那样**准备训练集做 LoRA 微调** —— 这正是本项目已经验证过的方法论。

## 为什么这个结果符合预期

一阶段的 0.6B 能用，不是因为它小，而是因为它在 4000 条样本上微调过，
system prompt + few-shot + 微调三者共同把行为固定下来。

二阶段换的是**一份新契约**（`planning_request.v1`）和一个**新任务**
（从杂乱文本抽多条待办 + 约束）。基座模型没见过，自然不会填。

> **换个角度：这个 52% 不是"方案不行"的证据，而是"必须走微调这条路"的证据。**
> 而微调恰好是这个项目最擅长、也最有把握的部分。

## 失败模式的定性观察

按失败原因归类（4B few-shot 的 10 个失败样本）：

| 失败类型 | 例子 | 占比 |
|---|---|---|
| **多件事抽不全** | "三件事：实验报告/论文/周报" 只抽到 1–2 条 | 最多 |
| **多件事的时长分配错** | "前两个各一小时，买菜半小时" 全填 60 | 多 |
| **约束漏抽** | "周三上午别排东西" 没生成 `keep_free` | 中 |
| **应澄清却拒答** | "帮我安排一下这周的事情" → `reject` 而非 `clarify` | 中 |
| **单件简单任务反而对** | "明天中午前交报销单，20 分钟" | — |

**规律：越短越准，越多越乱。** 单件 + 明确时长 → 基本能对；
三件以上 + 时长分散在句子里 → 明显吃力。

这说明**瓶颈是"多实体 + 属性绑定"**，不是理解中文本身。
这类问题恰好是**训练数据能系统性解决**的（反向构造法：先采样 3 条待办及其时长，
再渲染成中文，标签由构造保证正确）。

## 对二阶段计划的影响

| 原计划 | 调整 |
|---|---|
| "换个 4B 模型就能抽取" | ❌ 不成立，必须微调 |
| 先做客户端、后补数据 | ⚠️ 应改成：**先做规划抽取数据集 + 微调**，否则客户端没有可展示的链路 |
| 评估集 | ✅ 本文件里的 21 条可以直接作为微调后的回归集，也可以扩成训练集 |

### 建议的顺序（已按此调整）

```
1. planning 抽取数据集生成器（反向构造：采样待办结构 → 渲染中文）
   · 复用一阶段 gen_dataset.py 的"先定标签再渲染"思路
   · 覆盖：1/2/3/5 条待办、时长分散表达、keep_free、应拒答、应追问
2. 在 Qwen3-4B 上 LoRA 微调（一阶段 16 分钟一版，迭代快）
3. 用本文件 21 条做回归，目标 ≥85%
4. 达标后再接 /api/plan 和客户端
```

