# 抽取能力实测：二阶段的关键未知数

> 2026-11 实测。这是二阶段投入大量开发前必须先量出来的数字。
> 复现：`local/bench_extraction.ps1`

## 结论先说

### 一、21 条手写用例（v1，已弃用做结论）

| 模型 | 零样本 | few-shot×2 |
|---|---|---|
| Qwen3-1.7B | **14%**（3/21） | **33%**（7/21） |
| Qwen3-4B | **19%**（4/21） | **52%**（11/21） |

**★ 但这组数字不可用来做结论。** 21 条里差 1 条就是 5 个百分点，
95% 置信区间约 ±11 个百分点 —— 52% 和 47% 在统计上完全分不开。
后来我又试了 few-shot×5，得到 47%，比 52% "低"，但它们其实是同一个数。

### 二、留出测试集（v2，可信）

用 `gen_planning_dataset.py` 生成、与训练集无重叠的 100 条样本，
逐字段统计（`bridge/eval_on_dataset.py`，Wilson 95% 置信区间）：

| 指标 | Qwen3-4B 基座 + few-shot×5 | 95% CI | 样本数 |
|---|---|---|---|
| **status 判对** | **95.0%** | 89–98 | 100 |
| **item 平均 F1** | **0.926** | — | 100 |
| **duration 准** | **87.0%** | 82–91 | 239 |
| **deadline 准** | **52.6%** | 44–62 | 114 |
| **keep_free 准** | **30.6%** | 18–47 | 36 |
| **整条全对** | **4.0%** | 2–10 | 100 |

## 这个结果改变了诊断

**不是"抽不出来"，而是"不能同时全对"。**

- 判断该拒答还是该追问：95%（很容易）
- 抽出有哪几件事：F1 0.926（不错）
- 每件事多久：87%（不错，因为时长要么明说、要么有公认默认值）
- 日期说法有没有带出来：52.6%（弱）
- 排期约束有没有抽到：30.6%（最弱）

单看每个字段都还行，但一条样本里有 3 个事项 + 截止 + 约束时，
假设各字段独立，逐字段正确率相乘：0.87 × 0.53 × 0.31 ≈ 14%，
再叠加多事项的匹配误差，就掉到 4% 的"整条全对"。

---

## 关键发现：规则层比微调见效更快

既然 `keep_free` 只有 30.6%、`deadline` 只有 52.6%，而这两类恰恰**高度规则化**
（"周三上午别排"、"周五 18:00 前"），那就没必要让模型去做。

新增 `bridge/rules.py`：**模型负责语义（有哪几件事、该不该拒答），
规则负责结构化字段（时长、日期说法、排期约束）**。
这和一阶段"模型只做语义归一化、绝不计算日期"是同一条原则。

同样 100 条留出样本，只差规则开关：

| 指标 | 规则关 | 规则开 | 变化 |
|---|---|---|---|
| status 判对 | 95.0% | 95.0% | — |
| **整条全对** | **4.0%** [2-10] | **39.0%** [30-49] | **+35pp（≈10 倍）** |
| item 平均 F1 | 0.926 | 0.926 | — |
| duration 准 | 87.0% | 83.3% | -3.7pp（噪声内，见下） |
| **deadline 准** | 52.6% [44-62] | **100.0%** [97-100] | **+47pp** |
| **keep_free 准** | 30.6% [18-47] | **94.4%** [82-98] | **+64pp** |

关于 duration 的 -3.7pp：n=239 时标准误约 3.3pp，这个差异只有约 1.1 个标准误，
**统计上不显著**。两次独立运行都是 83.3%，说明规则层对时长基本无影响
（时长本来就多数来自标题默认值，规则只在分句里明说时才覆盖）。

**结论：不训练也能把"整条全对"从 4% 拉到 39%。**
这足以支撑一个能演示的原型；要上 80%+ 仍然需要微调，但优先级可以往后放。

### 规则层的设计要点

1. **只动三类字段**：`constraints` / `duration_min` / `deadline_*`。
   不改事项条数和标题 —— 那是模型的活，规则判断不了。
2. **约束优先抹除再处理**：先抽出 `keep_free` 并记下它的字符区间，
   把这些区间抹掉之后才去给事项找日期。否则
   "周三上午别排东西，写实验报告四小时" 会把"周三"错当成实验报告的截止日。
3. **定位不到就不改**：模型给的标题与文本对不上时直接用全文兜底，会抓到别的事项的
   时长把对的改错。找不到就保留模型原值。
4. **37 项单元测试**覆盖中文数字（"二十"→20）、"半小时"vs"一个半小时"、
   前缀式/后缀式约束、区间抹除、纯函数不改入参等。

### 另外两个观察到的事实

1. **few-shot 从 2 个加到 5 个没有提升**（都在噪声内）。说明瓶颈不在示例数量，
   而在模型本身不会这个任务。这进一步支持"必须微调"的结论。
2. **4B 每条约 6.7 秒**。真正交互时太慢，也说明最终产品要么用更小的微调模型，
   要么把 few-shot 去掉（微调后不需要）。

## 为什么这个结果符合预期

一阶段的 0.6B 能用，不是因为它小，而是因为它在 4000 条样本上微调过，
system prompt + few-shot + 微调三者共同把行为固定下来。

二阶段换的是**一份新契约**（`planning_request.v1`）和一个**新任务**
（从杂乱文本抽多条待办 + 约束）。基座模型没见过，自然不会填。

> **换个角度：这不是"方案不行"的证据，而是"必须走微调这条路"的证据。**
> 而微调恰好是这个项目最擅长、也最有把握的部分。

## 失败模式

留出测试集上的逐字段数字已经说明了问题（见上表），这里补充定性观察：

| 类型 | 具体表现 | 严重度 |
|---|---|---|
| **整条不自洽** | 单个字段大多对，但凑在一条里全对只有 4% | 🔴 最高 |
| **keep_free 漏抽** | "周三上午别排东西" 十次里七次抽不到约束 | 🔴 高 |
| **deadline 丢** | 抽出了待办但没带日期说法 | 🟠 中 |
| **多件事漏项** | "三件事"只抽到两件（F1 0.926 说明偶发） | 🟠 中 |

**共同点：瓶颈是"多实体 + 属性绑定 + 整体自洽"，不是理解中文。**
这类问题恰好是**反向构造训练集**能系统性解决的 —— 先采样结构化的多条待办及其属性，
再渲染成中文，标签由构造保证正确；模型从 4000 条里学到的是联合分布。

## 对二阶段计划的影响

| 原计划 | 调整 |
|---|---|
| "换个 4B 模型就能抽取" | ❌ 不成立 |
| 必须马上微调才能继续 | ⚠️ 已缓解：规则层把整条全对拉到 39%，够做原型了 |
| 先做客户端、后补数据 | ✅ 现在可以并行：数据/训练套件已就绪，客户端可以先做 |
| 评估集 | ✅ 已从 21 条手写升级为 100~344 条留出测试集，带置信区间 |
| few-shot 调参 | ❌ 已验证无效（2 个 vs 5 个都在噪声内），别再花时间 |

**修正后的优先级：**

```
P0  数据集 + 训练套件           ✅ 已完成（等你提供 GPU 就能跑）
P0.5 确定性规则层                ✅ 已完成，整条全对 4% → 39%
P1  plan_diff + 多轮对话        ← 现在就可以做，不再被抽取质量卡住
P2  客户端计划视图
P3  LoRA 微调（GPU 到位后，目标 80%+）
```

### 建议的顺序（已按此调整）

```
1. planning 抽取数据集生成器（反向构造：采样待办结构 → 渲染中文）
   · 复用一阶段 gen_dataset.py 的"先定标签再渲染"思路
   · 覆盖：1/2/3/5 条待办、时长分散表达、keep_free、应拒答、应追问
   · ✅ 已完成，4000 条，标签 100% 校验通过
2. 在 Qwen3-4B 上 LoRA 微调（一阶段 16 分钟一版，迭代快）
3. 用**留出测试集**做回归（`eval_on_dataset.py`，100 条起），目标「整条全对」≥80%
4. 达标后再接 plan_diff 和客户端
```

## 复现方法

```bash
# 1. 起模型（必须 --reasoning off，否则 4B 一个正文字都不出）
llama-server -m Qwen3-4B-Q4_K_M.gguf -ngl 99 -c 8192 --port 18999 --jinja -np 1 --reasoning off

# 2. 生成留出测试集（与训练集无重叠）
python pod/gen_planning_dataset.py --train 4000 --test 400 --outdir ./data-plan

# 3. 留出测试集评估（100 条，带置信区间，约 11 分钟）
.venv-planner\Scripts\python.exe bridge\eval_on_dataset.py \
    --data ./data-plan/test.jsonl --port 18999 --n 100 --fewshot-rich --label "4B 基座"

# 4. 21 条手写回归集（快速冒烟，不要用来下结论）
.venv-planner\Scripts\python.exe bridge\eval_extraction.py --port 18999 --fewshot-rich
```

## 备注：这组数字对参赛材料有用

这是一个**诚实的、量化的、有对比的**实验结果，比"我们的 AI 很智能"有说服力得多。

尤其值得写进技术报告的是**方法论**这一层：
1. 先量出瓶颈在哪（不是拍脑袋说"加个更大的模型就行"）
2. 发现 21 条样本的评估不可信（置信区间 ±11%），换成 100 条留出集
3. 逐字段拆开看，定位到真正的瓶颈是"整体自洽"而非"单点能力"
4. 据此决定走微调，而不是继续调 few-shot

标题可以是「**我们如何量化并定位二阶段的技术风险**」—— 展示的是工程判断力，
不是完美结果。
